## 컨텍스트 스위칭 

---

> 📖 
> 
> <a id="1c3eda9b0fe181f3a90dea480c7ed39e"></a>
> 
> 멀티스레드 환경에서 코어의 스레드 변경 시, 변경되는 스레드의 이전 작업 위치, 계산 변수 등을  메모리에서 다시 불러와 실행하는 작업

<details>
<summary>비유)  멀티태스킹 &#45; <strong><code>사람</code></strong></summary>

<a id="1c3eda9b0fe181c480bafc04ab78a3e6"></a>

비유를 하자면, 프로그램 A를 개발하고 있는데, 갑자기 기획자가 프로그램 B를 수정해달라고 요청한다&#46; 

<a id="1c3eda9b0fe181008f18c5d55263bd83"></a>

따라서 프로그램 A의 개발을 멈추고, 프로그램 B를 수정한다고 가정해보자&#46; 여기서 프로그램 B의 수정을 잘 마치고, 다시 프로그램 A를 개발하기 위해 돌아간다&#46; 

<a id="1c3eda9b0fe1818a9c9cf195a6a401c4"></a>

이때 이전의 작업으로 돌아가기 위해 비용이 든다&#46; 

- 먼저 프로그램 A의 어디를 개발하고 있었는지 해당 코드 위치를 다시 찾아야 한다&#46; 

- 변수들에 어떤 값들이 들어가는지 다시 해석하여 머리 속으로 불러와야 한다&#46; 

<a id="1c3eda9b0fe1812ca11eeb0099a41213"></a>

만약 프로그램 A의 개발이 다 끝나고, 프로그램 B를 수정한다면, 전체 시간으로 보면 더 효율적으로 개발할 수 있을 것이다&#46; 

</details>

<details>
<summary>멀티태스킹 &#45; <strong><code>컴퓨터</code></strong></summary>

- <strong><code>CPU 코어</code></strong>&#58; 1개 , <strong><code>스레드</code></strong>&#58; 2개 ( A, B )

<a id="1c3eda9b0fe181869845cad38536b0df"></a>

운영체제는 먼저 스레드 A를 실행한다&#46;  멀티태스킹 해야 하기 때문에, 스레드 A를 계속 실행할 수 없다&#46;  스레드 A를 잠시 멈추고, 스레드 B를 실행한다&#46; 

<a id="1c3eda9b0fe1813a90bac6193002956c"></a>

이후 스레드 A로  그냥 돌아갈 수 없다&#46; 

- CPU에서 스레드를 실행하는데, 스레드 A의 코드가 어디까지 수행되었는지, 위치를 찾아야 한다&#46; 

- 계산하던 변수들의 값을 CPU에 다시 불러들여야 한다&#46; 

<a id="1c3eda9b0fe181c48b21fcf86b683aca"></a>

따라서 스레드 A를 멈추는 시점에 CPU에서 사용하던 스레드 A의 작업 위치, 계산하던 변수들 등을 메모리에 저장해야 한다&#46; 그리고 이후에 스레드 A를 다시 실행할 때 이 값들을 CPU에서 다시 불러와야 한다&#46; 

<a id="1c3eda9b0fe181919e6dc11af4712623"></a>

이러한 과정을 <code>컨텍스트 스위칭( context switching )</code> 이라 한다&#46; 

<a id="1c3eda9b0fe18182869ada7e60046c84"></a>

<code>컨텍스트</code>는 <strong><u>현재 작업하는 문맥</u></strong>을 뜻한다&#46; <u>현재 작업하는 문맥이 변</u>하기 때문에 컨텍스트 스위칭이다&#46; 

<a id="1c3eda9b0fe181498c0df61614bf7d30"></a>

컨텍스트 스위칭 과정에서 이전에 실행 중인 값을 메모리에 잠깐 저장하고, 이후에 다시 실행하는 시점에 저장한 값을 CPU에 다시 불러와야 한다&#46;

<a id="1c3eda9b0fe18137a1d1d3fc199088e9"></a>

결과적으로 <strong><u>컨텍스트 스위칭 과정에는 약간의 비용</u></strong>이 발생한다&#46; 

</details>

<details>
<summary>멀티스레드는 대부분 효율적이지만, 컨텍스트 스위칭 과정이 필요하므로 항상 효율적인 것은 아니다&#46; </summary>

- ex)  1 &#126; 10000 더한다고 가정, 스레드는 2개 
    - 스레드1&#58; 1 &#126; 5000

    - 스레드2&#58; 5001 &#126; 10000

    - 마지막 <code>스레드 1</code>의 결과와 <code>스레드 2</code>의  결과를 더함



> CPU 코어&#58; <code>2개</code>

<a id="1c3eda9b0fe1815f8e35d63038bf7bed"></a>

CPU 코어가 2개 있다면, 스레드 1, 스레드 2로 나누어 멀티스레드로 병렬 처리하는게 효율적이다&#46; 

<a id="1c3eda9b0fe18197a92dc64319d70820"></a>

모든 CPU를 사용하므로 연산을 2배 빠르게 처리할 수 있다&#46; 

> CPU 코어&#58; <code>1개</code>

<a id="1c3eda9b0fe18131a443d3be761b99ac"></a>

CPU 코어가 1개 이지만  2개의 스레드를 만들어 연산 처리하면, 중간중간마다 컨텍스트 스위칭 비용이 발생한다&#46; 

<a id="1c3eda9b0fe1813f9717dc1e68fd7370"></a>

운영체제 스케줄링 방식에 따라 다르겠지만, 스레드1을 1 &#126; 1000 정도까지 연산한 상태에서 잠시 멈추고 스레드2를 5001 &#126; 6001까지 연산하는 식으로 반복할 수 있다&#46; 

<a id="1c3eda9b0fe1818a8e65c9b4ef8a8f4a"></a>

이때 CPU는 스레드 1을 멈추고 다시 실행할 때 어디까지 연산했는지 알아야 하고, 그 값을 CPU에 다시 불어와야 한다&#46;

<a id="1c3eda9b0fe181968837d896ba1f30cb"></a>

결과적으로 이렇게 반복할 때 마다 컨텍스트 스위칭 비용(시간)이 든다&#46; 

- <code>연산 시간</code>  &#43; <code>컨텍스트 스위칭 시간</code>

<a id="1c3eda9b0fe181dfb832effbfd169407"></a>

이런 경우, 단일 스레드로 1 &#126; 10000까지 더하는 것이 컨텍스트 스위칭 비용 없이, 연산 시간만 사용하기 때문에 더 효율적이다&#46; 

<a id="1c3eda9b0fe181ae9295e460b84af6d2"></a>

물론 최신 CPU는 초당 수 십억 단위를 계산하기 때문에 실제로는 계산에 더 큰 숫자를 사용해야 컨텍스트 스위칭이 발생한다&#46; 

</details>

<details>
<summary>참고 &#45; 실무 이야기 </summary>

<details>
<summary>CPU, 스레드 </summary>

- Case 1 )  CPU &#45; 4개, 스레드 &#45; 2개
    <a id="1c3eda9b0fe181e482a2fc5e9019b68b"></a>

    스레드의 숫자가 너무 적으면 모든 CPU를 100% 다 활용할 수 없지만, <br>스레드가 몇 개 없으므로 컨텍스트 스위칭 비용이 줄어든다&#46; 

- Case 2 )  CPU &#45; 4개, 스레드 &#45; 100개
    <a id="1c3eda9b0fe18119a69cd921726e50b2"></a>

    스레드의 숫자가 너무 많으면 CPU를 100% 다 활용할 수 있지만 컨텍스트 스위칭 비용이 늘어난다&#46;

- Case 3 )  CPU &#45; 4개, 스레드 &#45; 4개
    <a id="1c3eda9b0fe181bda942db5c2b1613d8"></a>

    스레드 숫자를 CPU 숫자에 맞춘다면 CPU를 100% 활용할 수 있고, 컨텍스트 스위칭 비용도 자주 발생하지 않기 때문에 최적의 상태가 된다&#46; 

    <a id="1c3eda9b0fe18125a0e5d05e95f40121"></a>

    이상적으로는 CPU 코어 수 &#43; 1개 정도로 스레드를 맞추면 특정 스레드가 잠시 대기할 때 남은 스레드를 활용할 수 있다&#46;

</details>

<details>
<summary><code>CPU 바운드 작업</code> vs <code>I / O 바운드 작업</code></summary>

- CPU 바운드 작업
    - CPU 연산 능력을 많이 요구 하는 작업을 의미한다 

    - 이러한 작업은 주로 계산, 데이터 처리, 알고리즘 실행 등 CPU 처리 속도가 작업 완료 시간을 결정하는 경우다 &#46;

    - ex) 복잡한 수학 연산, 데이터 분석, 비디오 인코딩, 과학적 시뮬레이션 등

- <code>I / O 바운드 작업</code>
    - 디스크, 네트워크, 파일 시스템 등과 같은 입출력(I/O) 작업을 많이 요구하는 작업을 의미

    - 이러한 작업은 I/O 작업이 완료될 때까지 대기 시간이 많이 발생하며, CPU는 상대적으로 유휴(대기) 상태에 있는 경우가 많다&#46; 

    - 쉽게 이야기해서 스레드가 CPU를 사용하지 않고 I / O 작업이 완료될 때까지 대기한다&#46; 

    - ex) 데이터베이스 쿼리 처리, 파일 읽기/쓰기, 네트워크 통신, 사용자 입력 처리 등

</details>

<details>
<summary>웹 애플리케이션 서버 &#45; 최적화된 스레드 수  ( 성능 테스트 )</summary>

<a id="1c3eda9b0fe181459115cf9cd93ab3a1"></a>

분야마다 다르지만, 실무에서는 <code>CPU 바운드 작업</code> 보다는 <code>I / O 바운드 작업</code>이 많다&#46; 

<a id="1c3eda9b0fe181529ad1d9fa8cc0989b"></a>

예를 들어서 백엔드 개발자의 경우, 주로 웹 애플리케이션 서버를 개발하는데 스레드가 1 &#126; 10000까지 더하는 CPU 연산이 필요한 작업보다는, <strong><u>대부분 사용자의 입력을 기다리거나, 데이터 베이스를 호출하고 그 결과를 기다리는 등</u></strong><strong> I/O 바운드 작업이 많다&#46; </strong>

<a id="1c3eda9b0fe181598f5bdd0e15e776b4"></a>

따라서 스레드가 CPU를 많이 사용하지 않는다&#46; 

<a id="1c3eda9b0fe18136bbdbededaa6e3a00"></a>

일반적인 자바 웹 애플리케이션 서버의 경우, 사용자의 요청 하나를 처리하는데 1개의 스레드가 필요하다&#46; 

<a id="1c3eda9b0fe18175af40e9d7f1580db7"></a>

사용자 4명이 동시에 요청하면 4개의 스레드가 작동하는 것이다&#46; 

<a id="1c3eda9b0fe181f8b4b5c08a03cecef8"></a>

그래야 4명의 사용자 요청을 동시에 처리할 수있다&#46; 

<a id="1c3eda9b0fe181048b88e8ac29f56eae"></a>

예를 들어 <strong><u>사용자의 요청을 하나 처리</u></strong>하는데 <strong><u>스레드는 CPU를 1% 정도 사용</u></strong>하고, 대부분 데이터베이스 서버에 어떤 결과를 조회하면서 기다린다고 가정한다면, 이때 <strong><u>스레드는 CPU를  거의 사용하지 않고 대기</u></strong>한다&#46; 

<a id="1c3eda9b0fe1814cbe9ecf1642f5fb33"></a>

바로 <strong><u>I/O 바운드 작업이 많다</u></strong>는 것이다&#46; 이 경우 CPU 코어가 4개 있다고 해서 스레드 숫자도 CPU 코어에 맞춰 4개로 설정하면 안된다&#46; 그러면 동시에 4명의 사용자 요청만 처리할 수 있다&#46; 

<a id="1c3eda9b0fe1810ca1afec4a7a03d4af"></a>

이때 CPU는 단순하게 계산해서 4% 정도만 사용할 것이다&#46;

<a id="1c3eda9b0fe18164a1bad9c8e2fad4ea"></a>

 결국 사<strong><u>용자는 동시에 4명 밖에 못</u></strong>받지만 <u>CPU는 4%만 사용</u>되어 <u>나머지 CPU가 놀고 있는 사태</u>가 벌어질 수 있다&#46; 

<a id="1c3eda9b0fe181b2bf1ad1188af2c39b"></a>

사용자의 요청 하나를 처리하는데 CPU를 1%만 사용한다면 단순하게 생각해도 100개의 스레드를 만들 수 있다&#46; 이렇 게 하면 동시에 100명의 사용자 요청을 받을 수 있다&#46; 물론 실무에서는 <strong><u>성능 테스트를 통해서 최적의 스레드 숫자를 찾는 것이 이상적</u></strong>이다&#46;

<a id="1c3eda9b0fe181a88c85f7d424db152e"></a>

결국 스레드 숫자만 늘리면 되는데, 이런 부분을 잘 이해하지 못해서 서버 장비에 문제가 있다고 생각하고 2배 더 좋은 장비로 구매하는 사태가 발생하기도 한다&#33; 이렇게 되면 CPU는 4%의 절반인 2%만 사용하고 사용자는 여전히 동시에 4명 밖에 받지 못하는 사태가 벌어진다&#46;

<a id="1c3eda9b0fe1813cbe7ad62831ce1615"></a>

정리하면 스레드의 숫자는 CPU&#45;바운드 작업이 많은가, 아니면 I/O&#45;바운드 작업이 많은가에 따라 다르게 설정해야 한다&#46;

- <strong>CPU&#45;바운드 작업</strong>
    - CPU 코어 수 &#43; 1개

    - CPU를 거의 100% 사용하는 작업이므로 스레드를 CPU 숫자에 최적화

- <strong>I/O&#45;바운드 작업</strong>
    - <strong>CPU 코어 수보다 많은 스레드를 생성</strong>

    - <strong>CPU를 최대한 사용할 수 있는 숫자까지 스레드 생성</strong>

    - <strong>CPU를 많이 사용하지 않으므로 성능 테스트를 통해 CPU를 최대한 활용하는 숫자까지 스레드 생성</strong>

    - <strong>단 너무 많은 스레드를 생성하면 컨텍스트 스위칭 비용도 함께 증가한다&#46;</strong>
        - <strong>적절한 성능 테스트 필요</strong>

<a id="1c3eda9b0fe18137ae7bfd061e2840e4"></a>

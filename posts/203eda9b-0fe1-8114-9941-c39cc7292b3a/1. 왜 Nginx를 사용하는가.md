> 어떤 기술을 배우기 전에, 무작정 해당 기술을 배우기 보다는 왜 이 기술을 배우는지, 어떤 것 때문에 해당 기술을 학습 해야하는지 그 목적성을 가진 뒤에 그 다음에 학습을 들어가는 것이 좋다&#46; 

<a id="203eda9b0fe180d7a50df32038784bf9"></a>

### Nginx를 왜 배우는 것인가?

---

<a id="203eda9b0fe180509c52ecfec8de6fa7"></a>

Nginx는 현업에서 안 쓰고 있는 기업을 찾기가 어려울 정도로 많이 사용하는 프로그램이다&#46; 

<a id="203eda9b0fe180c1936ddb534bbea932"></a>

현업에서 많이 쓰고 있다는 건, (벡엔드) 개발자로 취업하기 위해 필수로 알아야 하는 기술이라는 뜻이다&#46; 

> 그러면 Nginx는 어떤 역할을 하는 것인가?

<a id="203eda9b0fe1808e92b5df7cc884e25f"></a>

Nginx는 여러 기능을 제공하는 소프트웨어이다&#46; <br>해당하는 기술들은 아래와 같다&#46; 

- 정적 컨텐츠 제공

- SSL 처리 ( <code>HTTPS</code> )

- 로드 벨런싱

- 장애 대응

- 캐싱

- 보안 처리 ( IP 차단, 요청 수 제한 )

<a id="203eda9b0fe180ac81a9c1b5d08293d4"></a>

Nginx가 제공하는 기능들은 실제 서비스를 운영할 때 필수적으로  사용하는 기술들이다&#46; 

<a id="203eda9b0fe180bab302ed44df7afd41"></a>

### 그렇다면 왜 Nginx인가? 

---

<a id="203eda9b0fe1800c8994c5705319ccb4"></a>

다른 기술들과 비교한 내용은 아래와 같다&#46; 

| <strong>항목</strong> | <strong><code>Nginx</code></strong> | <strong><code>Apache</code></strong> | <strong><code>Node&#46;js</code></strong><strong>(</strong><strong><code>Express</code></strong><strong>) 직접 서빙</strong> | <strong><code>HAProxy</code></strong> |
| --- | --- | --- | --- | --- |
| 성능 <br>(처리량, 속도) | ✅ 이벤트 기반, 매우 빠름 | ❌ 스레드 기반으로 느림 | ❌ 동시 처리 어려움 | ✅ 고성능 |
| 리소스 사용 | ✅ 메모리 적음 | ❌ 메모리 많이 사용 | ❌ Node는 비효율적 | ✅ 효율적 |
| HTTPS/SSL 처리 | ✅ 안정적, 기본 지원 | ✅ 지원 | ❌ 별도 설정 필요 | ❌ SSL 미지원 (보통 Nginx와 함께 씀) |
| 정적 리소스 제공 | ✅ 매우 빠름 | ✅ 빠름 | ❌ 비효율적 | ❌ 지원 안함 |
| 로드 밸런싱 | ✅ 기본 지원 | ✅ 모듈 필요 | ❌ 미지원 | ✅ 전용 기능 |
| 생태계 &#38; 문서 | ✅ 풍부, 대부분 예제가 Nginx 기준 | ⚠ 오래되고 복잡함 | ⚠ 설정 어렵고 정보 부족 | ✅ 고급 사용자가 주로 사용 |

<a id="203eda9b0fe18084b2c3d7472dbadf75"></a>

위와 같이 다른 기술들과 비교했을 때, Nginx가 더 뛰어난 운영 환경을 제공한다&#46; 

- <strong>Nginx는 </strong><strong><u>‘올인원 역할’</u></strong><strong>을 할 수 있어 운영 효율성이 좋다&#46;</strong>

<a id="203eda9b0fe1800dab62d6cb366dfcb8"></a>

<strong><br>또한 Nginx는 “개발자 혼자 구현하기 어렵고 민감한 기능”들을 신뢰성 있게 제공한다&#46;</strong>

| <strong>기능</strong> | <strong>Nginx 지원</strong> | <strong>직접 구현 시 어려운 이유</strong> |
| --- | --- | --- |
| HTTPS/SSL | 🔐 자동 인증서 연동 <br>(Let’s Encrypt, certbot) | OpenSSL, 키 관리 등 복잡 |
| 요청 제한 | 🔒 IP별 요청 수 제한 (limit&#95;req&#95;zone) | WAS에서 구현하려면 상태 추적 필요 |
| 캐싱 | ⚡ 설정만으로 API 응답 캐싱 | 직접 구현하면 Redis 등 추가 필요 |
| 장애 대응 | 🔁 서버 다운 시 대체 서버로 우회 | 직접 구현 시 health check &#43; failover 구성 필요 |

- 위와 같은 기능들을 <strong>WAS(Spring, Express 등)</strong> 에서 직접 구현하려면 <strong>복잡한 코드, 보안 이슈, 성능 문제</strong>가 생기고 운영자가 직접 관리하기 매우 힘들다&#46;

<a id="203eda9b0fe180bc9bd6f09baf441d03"></a>

### 실제 현업 사용 

---

<a id="203eda9b0fe1803a9c71fa8d267e7b4e"></a>

```yaml
사용자 → Nginx (80/443 포트) 
          ├─> 정적 파일 (React, Vue 빌드 결과물)
          └─> Spring Backend (JWT, DB 등 동적 처리)
```

- SSL은 Nginx가 처리함 (https&#58;//your&#45;domain)

- 프론트 요청은 index&#46;html 정적 파일 반환

- API 요청은 내부 WAS로 전달 (/api/&#42;&#42; → localhost&#58;8080)

- 요청 수 제한, 캐시, Gzip 압축도 전부 Nginx에서 수행

> 🗒️ 
> 
> <a id="203eda9b0fe180f1ba87d3866a15af1f"></a>
> 
> <strong>&#91;정리&#93; </strong><strong><code>Nginx</code></strong><strong>를 기업들이 선택하는 이유</strong>
> 
> ---
> 
> - <strong>높은 성능</strong> (Event 기반 아키텍처)
> 
> - <strong>다양한 기능을 하나로 통합</strong> (SSL, 정적 서버, 프록시, 캐시, 제한 등)
> 
> - <strong>보안과 트래픽 제어에 강함</strong>
> 
> - <strong>간단한 설정만으로 많은 기능 제공</strong>
> 
> - <strong>전 세계적으로 대규모 서비스에서 입증된 안정성</strong>
> 
> - <strong>Spring, Node&#46;js, PHP 등 어떤 백엔드와도 잘 연동</strong>
> 
> ---
> 
> <a id="203eda9b0fe1804492e1e1c75691cf77"></a>
> 
> 개발자라면 <code>Nginx</code>는 선택이 아닌 필수이다&#46;
> 
> <a id="203eda9b0fe1801cbcf5d62120f4f504"></a>
> 
> 특히 <u>대규모 트래픽 처리, DevOps 자동화, 고가용성 인프라 설계</u> 에선 거의 표준이다&#46;

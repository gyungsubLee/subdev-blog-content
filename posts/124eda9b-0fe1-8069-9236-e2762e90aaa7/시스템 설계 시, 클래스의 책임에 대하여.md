> 학습 하다가 든, 의문점들을 ‘최원빈’ 튜터님께 질문하여 답변 받음

<a id="cd28c421e8ee41879bcf0378921c5dd8"></a>

### 1&#46; 질문 정의

<a id="14f227bc252f4ea8bfb844f280cdb955"></a>

산책을 하면서 프로젝트(계산기)  코드를 리마인드 하던 중 문득 의문점이 생겼다&#46;

<a id="2964b82bb7f74a2386807a894a13b73b"></a>

 

<a id="40125f769c3c4a179cdae275cec351f0"></a>

&#91;과제&#45;계산기&#93;를 설계함에 있어서 SOLID 원칙을 준수하려고 

<a id="047c27d3c687458e89de0b88b6bc6d10"></a>

게산 결과를 <code>저장</code>, <code>삭제</code>, <code>수정 </code>로직을 아래와 같이 interface로 분리 후 구현하였다&#46; 

<details>
<summary>&#91; 코드 &#93; &#60; interface &#62; CalculationResultRepository</summary>

<a id="69f9bb876a7f4663942708486ac98049"></a>

```java
public interface CalculationResultRepository {
    void addResult(double result);
    Queue<Double> getResults();
    void removeResult();
}
```

</details>

<details>
<summary>&#91; 코드 &#93; CalculationResultRepositoryImp</summary>

<a id="eb1c72d6c0eb434e97da1369da0554e7"></a>

```java
public class CalculationResultRepositoryImp implements CalculationResultRepository{
    private final Queue<Double> results = new LinkedList<>();

    @Override
    public void addResult(double result){
        results.add(result);
        System.out.println("계산한 결과 값인  '" + result + "' 가 저장 되었습니다.");
    }

    @Override
    public Queue<Double> getResults(){
        return results;
    }

    @Override
    public void removeResult() {
        Double removeNumber = results.remove();
        System.out.println("저장된 결과 값인  '" + removeNumber + "' 가 삭제 되었습니다.");
    }
}
```

</details>

<a id="b630648e3b704a6aa801318b29f08077"></a>

여기서 의문점이 들었다&#46;

<a id="d28e2f9ba12041b8b07658899cbef64d"></a>

&#91; SOLID &#45; SRP, 단일 책임 원칙 &#93; 을 따르면 <u>한 클래스에는 하나의 책임만을 설계해야 한다</u>

<a id="57d30663a1b94c07b5b7bf9b72606630"></a>

그렇다면  ‘🧐 위 저장소(CalculationResultRepositoryImp) 클래스는 <strong><u>3가지의 책임(저장, 조회, 삭제) </u></strong><strong>이 정의된 것이 아닌가?’</strong>

<a id="47d8807b223f44f9bc026af7a7a300ed"></a>

그러나 이 부분에 있어서 이전 스프링 강의(인프런&#45;김영한)를 학습할 때,  <strong><u>SRP, OCP, DIP, 다형성</u></strong>을 준수한 방법으로 <strong><u>3 Layer Architecture ( Contoller &#45; Service &#45; Repository)</u></strong> 로 나눠 각  <strong><u>interface</u></strong>를 만들고 <code>DI(의존성 주입)</code>를  통해 구현한다고 배웠었다&#46;

<a id="3943d061a3424060b48af3b51660f1e2"></a>

그렇다면,  Controller, Service, Repository는 각각 하나의 책임을 가지고 있다는 뜻이고,

<a id="d5691b8ebeb449fe8d33e3163965a027"></a>

이는 <code>저장</code>, <code>삭제</code>, <code>수정</code> 보다 한 층 더 높은 layer로 책임을 정의한다는 뜻이다&#46; 

<a id="90f15a2e76264e04ae5ecf334129ede0"></a>

여기서 또 다른 의문점들이 들었다&#46; 

> Q&#58; 🧐 단일 책임 원칙에서 정의하는 <strong><u>하나의 책임에 대한 범위</u></strong>는 어디까지 인가? <br>          <code>저장</code>, <code>삭제</code>, <code>수정</code>  묶어서 하나의 책임으로 정의하는 것이 올바른가?

> Q&#58; 🧐 예전 스프링 강의(인프런&#45;김영한)  학습 시, 예시로  <code>3 Layer Architecur</code>를  각 도 메인(회원, 주문…)별로 생성하여 진행했는데, 여기서 도메인은 어떠한 의미를 가지는가? 이것도 책임이라고 정의해야 하는가?

<a id="fd33d8119f9c40f1a7093bfc370da2d0"></a>

이 부분에 대해서 도움을 얻고자, 튜터님께 질문하였다&#46; 

<a id="10b509d6aa124d86aa4d1686a1c0db0c"></a>

### 2&#46; 질문 답변

<details>
<summary>1&#46;  🧐  <code>저장</code>, <code>삭제</code>, <code>수정</code>  묶어서 하나의 책임으로 정의하는 것이 올바른가?</summary>

<a id="ea69dab6832345ed9f4b85f851b5bc14"></a>

위 저장소의 구현체(<code>CalculationResultRepositoryImp</code>)는 ‘하나’ 이다&#46; 

<a id="e026f11126274759bc3294794cdcdb14"></a>

따라서 데이터를 저장하고 관리하는 ‘저장소의 기능’을 책임으로 정의한다&#46;

<a id="03ba751e84644e4f9c9462ae82af641d"></a>

‘ ‘데이터를 어떻게 처리할 거냐? ‘ 라는 부분에 있어서 ‘처리’에  CRUD가 포함된다&#46; 

<a id="0a236bf8c7dc428c8719003d9cb6da4e"></a>

그리고 이 처리는 저장소를 통해 이뤄진다&#46; 따라서 ‘<strong><u>저장소의 기능’을 책임으로 정의</u></strong>하는 것이 

<a id="d3ed81353e744a58a16c1c9eca853294"></a>

<code>저장</code>, <code>삭제</code>, <code>수정을</code> 하나의 책임으로 정의하는 것보다<strong><u> 더 올바른 책임의 분리</u></strong>이다&#46;<br>

> 추가) 그렇다면 다른 책임에 대한 에시들이 있는가? 

<a id="0ae0647ac35047afa6bc57db7028139e"></a>

<code>3 Layer Architecur</code>를 예시를 들어 설명하자면 각 책임들은 아래와 같다&#46;

<a id="64a40e969e774d7f82128ed9cc5cfb9f"></a>

```plaintext
컨트롤러 - 입출력
서비스 - 비지니스 로직
리포지토리 - 영속화. DB 관리
```

</details>

<details>
<summary>2&#46; 🧐 예전 스프링 강의(인프런&#45;김영한)  학습 시, 예시로  <code>3 Layer Architecur</code>를  <strong><u>각</u></strong><strong><u> 도메인(회원, 주문…)별로 구분</u></strong>하여 진행했는데, 여기서 <em><u>도메인은 어떠한 의미 </u></em>를 가지는가? 이것도 책임이라고 정의해야 하는가?</summary>

<a id="6ca8a06f22e1473db7e69e3666d616bd"></a>

우선 도메인은 책임이 아니다&#46;

<a id="9445c33b164c4038bbb4e7a876ed18b2"></a>

만약 하나의 서비스에서 앱의 모든 비지니스 로직을 관리하면 무수히 많은 사이드 이펙트들이 발생된다&#46; 이를 위해<strong><u> 패키지 화</u></strong> 하여  <strong><u>도메인 별로 구분하여 독립적으로 만드는 것</u></strong>이다&#46;<br> 이로 인해 <strong><u>확장에 유연</u></strong>하고, <strong><u>유지보수를 더 편리</u></strong>하게 만들어준다&#46; 

<a id="8db7e10da6ad4119866e49fc585043e6"></a>

이렇게 <strong><u>도메인 단위</u></strong>로 묶어서 개발하는 방식을 ‘도메인 주도 개발(Domain&#45;Driven Design, DDD)’ 이라고 한다&#46;

</details>

<details>
<summary>3&#46; 클래스에 설계할 때, 어느정의 책임까지 줘야하느냐?</summary>

<a id="5bc765e1b8af4e5f950d6cbb7382ec93"></a>

시스템을 설계한다면 , 해당하는 클래스에 어느 정도에 책임을 줘야하는지에 대해 고민을 하게 되는데 이때, 이후 상황까지 고려해서 설계를 해야한다

<a id="d7684e7af5074ba5a6c6e774f000c46a"></a>

예시로 결제를 담당하는 도메인을 설계하는데, 결제가 끝나고 반드시 알람을 보내야한다면, 

<a id="fff7c005fb804ddba28ab8feddc43572"></a>

payment(결제) 클래스에는 어느 정도의 책임을 줘야하는가?

> 이벤트 기반 아키텍처(Event&#45;Driven Architecture, EDA)

<a id="e384c82a89454f1e9a893361ae95ca0f"></a>

알람 도메인을 분리 후, 개발을 진행한다면 결제가 끝나고 알람을 보낼 시, 중간 과정이 생긴다&#46;

> 이벤트를 받아서, 트리거 생김 → 동작에 한 스텝이 더 증가함 → 오류 발생 확률 증가

<a id="14f0a91928b44a25a3f45ad6297be13d"></a>

해당 알람이 서비스 기획적으로 반드시 전달되어야 하는데, 만약 중간에 네트워크 손실이 발생되고 이에 따라 알람이 가지 못한 경우가 생긴다면 오히려 도메인을 분리하여 책임을 나눠서 설계하는 것더 리스크가 큰 설계가 된다&#46; 

<a id="b15a3e828dc84ee2bbb95cbea90058bc"></a>

이런 경우에는 아에 책임을 합쳐서 하나의 클래스로 설계를 한다&#46;

<a id="344b94955e4545419107258caf2ab00d"></a>

무조건적으로 책임의 범위가 정해져 있다고 생각하면 안되며, 항상 정답은 없다&#46;

<a id="83099a20b62e4981a5ca650ab1653d75"></a>

상황에 따라 중요도 및 리스크를 판단하여 유동적으로 설계해야 한다&#46; 

</details>

### 3&#46; 정리 

<a id="5576c83cb0434928bcd9a382b5de988c"></a>

설명해주신 내용이 이것보다 훨씬 자세하고 다양 했는데, 타자가 느린 관계로 다 적지 못했다…

<a id="9f219679fcb8461494095b810c05a02d"></a>

상황에 따라 클래스에 대한 책임 범위는 사스템 설계에 대한 고민으로 관련 레퍼런스들이 많다고 하셨다&#46;

- 추천 책)  가상 면접 사례로 보는 시스템 설계, 오브젝트

<a id="0d7c80873311451cb8d60054be9cafb3"></a>

우선 경험을 많이 해봐야지 실력적으로 늘어나는 부분이라고 하셨다&#46;

<a id="cc56f2677ac740e0a94f9131544652d4"></a>

책임은 논리적인 개념으로, 비지니스에 맞춰 책임을 분리하고 통합하는 것은 경험치 나 숙련도가 큰 비중을 차지한다고 하셨다&#46;

<a id="41b992cde877422985758b67248cb328"></a>

또한 관련 참고자료들을 학습할 때도, 해당 내용들은 그 상황에 대한 내용들 이지, 내가 직접 시스템을 설계한다고 한다면 해당 내용을 잘 숙지하지 못한다고 하셨다&#46;

<a id="2ebb72cbbfc043afaf8107242812a8f8"></a>

따라서 강의, 블로그 등을 통한 레퍼런스로 학습을 한 후, <strong><u>‘내가 이 개념을 완전히 이해 했는가?</u></strong>’ 에 대해서는<strong><u> </u></strong><strong><u>다른 상황에 적용</u></strong>해 볼 수 있을 정도로 <strong><u>추가적인 학습을 진행</u></strong>하는 것이 좋다고 하셨다&#46;

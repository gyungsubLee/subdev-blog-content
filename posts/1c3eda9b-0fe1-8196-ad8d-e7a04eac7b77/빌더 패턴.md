## 객체 지향 &#45; <code>불변성</code>, <code>일관성</code>

---

> ☝🏻 
> 
> <a id="1c3eda9b0fe18142953bc0c675b10075"></a>
> 
> 객체 지향 프로그래밍에서 객체의 상태의 <code>불변성</code> 과  <code>일관성</code>은 객체의 안정성과 신뢰성을 보장할 수 있다&#46;
> 
> <a id="1c3eda9b0fe181cda530dfff500f36cd"></a>
> 
> 이렇게 객체를 일관성 있고 불변하게 설계하면 소트프웨어를 유지보수 및 디버깅하기 쉽게  만들 수 있다&#46; 

<details>
<summary>🤬<strong><u> 외부에서 객체의 상태를 변경</u></strong>할 수 있으면 생기는 <strong><u>오류 상황</u></strong></summary>

<a id="1c3eda9b0fe18197b9d8d61a819fc519"></a>

<strong><u>외부에서 객체의 상태를 변경할</u></strong> 수 있는 객체를 <code>가변 객체</code>라 한다&#46;

<a id="1c3eda9b0fe181dc89b8defc41709ee2"></a>

이러한 가변 객체는 다양한 오류를 초래할 수 있다&#46;

> 실무에서 발생될 수 있는 몇 가지 오류 상황 예시

<details>
<summary>🧐 데이터의 무결성</summary>

- 데이터의 <strong><code>정확성</code></strong><strong>, </strong><strong><code>일관성</code></strong><strong>, </strong><strong><code>신뢰성</code></strong>을 보장하는 것을 의미한다&#46;

- 데이터가<strong><u> </u></strong><strong><u>생성, 저장, 처리되는 동안 본래의 의미와 값을 유지할 수 있도록 보장</u></strong>하는 중요한 데이터 관리 원칙이다&#46; 

- 무결성을 통해 <u>데이터베이스 와 시스템의 안정성을 유지</u>하고 <u>신뢰할 수 있는 데이터를 제공</u>할 수 있다&#46; 

</details>

<details>
<summary><strong>1&#46; 스레드 안전성 문제</strong></summary>

<a id="1c3eda9b0fe181e0b0f9ca05efee56de"></a>

가변 객체가 <strong><u>여러 스레드</u></strong><u>에서 </u><strong><u>동시에 접근</u></strong><u>되고</u><strong><u> 변경</u></strong>될 수 있는 경우, <strong><u>예상치 못한 동작</u></strong>이나 <strong><u>데이터 불일치</u></strong>가 발생할 수 있다&#46;

- 동시성 이유
    <a id="1c3eda9b0fe181f1be4dd7322747db0f"></a>

    <u>다중 스레드 환경</u>에서 <strong><u>필드가 수정될</u></strong> 때, <u>스레드가 동기화 되지 않</u>으면 <strong><u>서로 다른 스레드</u></strong>가<strong> </strong><strong><u>동시에 </u></strong><strong>해당 필드를 읽고 변경</strong>하여 최종적으로 일치하지 않는,<strong> </strong><strong><u>무결성을 해치는 데이터가 필드에 할당</u></strong>된다&#46;

- 데이터 레이스 
    <a id="1c3eda9b0fe181ec8e40c3d74572a72b"></a>

    한 스레드가 객체의 상태를 변경하는 중, 다른 스레드가 그 값을 읽어가면, <u>최종적으로 변경 되기 전, 이전 상태의 데이터가 사용될 수 있</u>어 프로그램이 비정상적으로 동작할 수있다&#46;<br>

</details>

<details>
<summary>2&#46; 데이터 무결성 문제 </summary>

<a id="1c3eda9b0fe18167a52efc250ec79f2d"></a>

<u>외부에서 객체 상태가 예상치 못하게 변경</u>되어 <strong>데이터의 무결성을 해칠 수 있</strong>다 &#46;

- 유효하지 않는 상태 값 할당
    <a id="1c3eda9b0fe181858b25f492928b956f"></a>

    양수의 값을 가져하는 필드(상태)인 경우(ex,  <code>Person</code>,<code>age</code>), <u>외부에서 음수 값을 설정</u>하여 유효하지 않는 상태값이 할당될 수 있다&#46;

    <a id="1c3eda9b0fe181749b30cfadb9eeb1e0"></a>

    이로 인해, 해당 객체가 사용되는 다른 로직에서 문제가 발생된다&#46; 

    <a id="1c3eda9b0fe181dd9a50f6063c3e841f"></a>

    이렇게 <strong><u>객체의 상태(필드)의 속성을 헤치는 값</u></strong>이 <strong><u>외부에서 할당</u></strong><em><strong> </strong></em>될 수 있다&#46; 

- 일관성 깨짐
    <a id="1c3eda9b0fe181d4b4cae30c72440304"></a>

    한 객체의 상태가 다른 객체의 상태에 의존할 때

    <a id="1c3eda9b0fe181799d2dc8f64211a069"></a>

    외부에서 객체의 상태가 변경되는 경우, 의존된 객체에서의 해당 상태가 업데이트 되지 않을 수 있다&#46; 

    <a id="1c3eda9b0fe1811cb886fe35572fcfde"></a>

    따라서 객체 상태가 다른 객체에서는 다른 값을 가지게 된다&#46;  즉, 일관성이 깨진다&#46;

<a id="1c3eda9b0fe181edad1ce902d78c35e2"></a>

 

</details>

<details>
<summary>3&#46; 의도하지 않은 상태 변경</summary>

- 참조에 의한 변경
    <a id="1c3eda9b0fe18181ae67f8ce39437634"></a>

    객체가 다른 객체에 의해 참조되고 있을 때, 해당 객체의 상태가 외부 코드에 의해 변경되면 이를 참조하고 있는 모든 코드에영향을 줄 수 있다&#46; 

    - ex)
        - 리스트나 맵 같은 컬렉션 객체가의 상태가 변경되면,<br>예상치 못한 곳에서 요소가 추가되거나 제거될 수 있다&#46; 

- 불투명한 변경 
    - 객체의 상태가 외부에 의해 변경되면, 참조하고 있는 다른 로직이 해당 객체의 변경되었다는 사실을 알 수 없다&#46; <br>따라서 의도와 다르게 프로그램이 비정상적으로 동작될 수 있다&#46; 

</details>

<details>
<summary>4&#46; 디버깅과 유지보수 어려움</summary>

- 디버깅 복잡도 증가
    <a id="1c3eda9b0fe18118889ef301a885ef4a"></a>

    디버깅 시 객체의 상태가 언제, 어디서, 어떤 이유로 변경되었는지 추적하기가 어려워지며, 이는 버그 발생 원인을 찾는데 많은 비용을 소모하게 한다&#46; 

- 예상치 못한 사이드 이펙트
    <a id="1c3eda9b0fe18135a6a9ee3a2181e80f"></a>

    외부에서 객체 상태를 변경할 때, 다른 코드에서 부수적인 영향이 발생될 수 있어 유지보수가 어려워진다&#46; 

    <a id="1c3eda9b0fe1819ca964daae40c6b4bc"></a>

    예를 들어, 한 메서드가 객체의 상태를 변경하면, 참조하던 다른 메서드의 로직이 의도한 대로 동작하지 않을 수 있다&#46; 

</details>

<details>
<summary>5&#46; 보안 문제</summary>

<a id="1c3eda9b0fe1812a9056fe2137338615"></a>

민감한 데이터나 중요한 상태를 외부에서 변경할 수 있는 경우,<br>이를 악용하여 시스템 동작을 예기치 않게 바꿀 수 있다&#46; 

- 취약점 악용, 무결성 훼손

</details>

<a id="1c3eda9b0fe181edbc8ffccd8d7de8db"></a>

외<strong><u>부에서 변경 가능한 가변 객체</u></strong>는 <strong>의도하지 않는 상태 변경을 일</strong>으켜  <strong><code>데이터의 무결성 문제</code></strong><strong>, </strong><strong><code>스레드 안정성 이슈</code></strong><strong>,</strong><strong> </strong><strong><code>디버깅 어려움</code></strong><strong>,</strong><strong> </strong><strong><code>보안 문제</code></strong> 등의 다양한 오류 상황을 초래할 수 있다&#46; 

<a id="1c3eda9b0fe18179af5bef50164c701e"></a>

<br>따라서 이를 방지하기 위해선, <strong><u>불변 객체</u></strong>를 사용하거나, <u>객체의 상태를 변경할 수 있는 메서드</u>에<strong><u> </u></strong><strong><u>적절한 접근 제어</u></strong>와 <strong><u>검증 로직</u></strong>을 추가하는 것이 중요하다 &#46;

</details>

<details>
<summary>불변성 ( <strong>Immutability )</strong></summary>

<a id="1c3eda9b0fe1815ba0aaf4b5aaa42655"></a>

<strong>불변성</strong>이란 <u>객체가 생성된 후</u> 그 <u>상태(필드 값)가 변경되지 않</u>도록 하는 것을 의미한다&#46; 

<a id="1c3eda9b0fe1815e979ff1f1d4edf32e"></a>

따라서 <u>외부에서 객체의 상태를 변경할 수 없</u>다&#46; 

<details>
<summary>장점</summary>

- 스레드 안정성
    - 여러 스레드에서 동시에 접근해도 상태가 변하지 않으므로 동기화 문제를 방지할 수 있다&#46;

- 예측 가능성
    - 불변 객체는 한 번 생성되면 그 상태가 바뀌지 않기 때문에 예측 가능한, 즉 의도한 대로의 동작되도록 한다&#46; 

- 안정성
    - 객체의 상태가 변하지 않으므로 불변 객체는 복사할 필요없이 안전하게 공유될 수 있다&#46; <br>

</details>

<details>
<summary>객체의 상태(필드)에 불변성 적용 </summary>

<a id="1c3eda9b0fe1818a967cd84a103ee68c"></a>

```java
public final class ImmutableObject {
    private final String value;
		
		// 생성자 주입
    public ImmutableObject(String value) {
        this.value = value;
    }

    public String getValue() {
        return value;
    }
}
```

- <code>private</code>, <code>final</code> 키워드를 사용하여 필드(상태) 값를 불변하게 만든다&#46;
    - <code>private</code>&#58; 외부 접근 불가, 동일 클래스 내에서만 접근 가능

    - <code>final</code>&#58; 재할당 불가

- 생성자 주입
    - 생성자를 사용하여 객체 생성 시에만 값을 할당할 수 있도록 한다&#46;

</details>

</details>

<details>
<summary>일관성 ( <strong>Consistency ) </strong></summary>

<a id="1c3eda9b0fe181379348f81415a32765"></a>

일관성이란 객체가 <strong><u>항상 유효한 상태를 유지</u></strong>하도록 <strong><u>보장</u></strong>하는 것을 말한다 &#46;

<a id="1c3eda9b0fe18163b730ee6054e49311"></a>

즉, 객체의 상태가 <strong><u>어떤 조건이나 규칙을 항상 만족</u></strong>하도록 <strong><u>유지</u></strong>하는 것을 의미한다&#46; 

<a id="1c3eda9b0fe181cc9cfcc9d14b8bdfc0"></a>

객체가 생성되거나 메서드가 호출될 때 <u>상태가 유효하지 않</u>다면, 프로그램이 <u>예상치 못하게 동작할 수 있</u>기 때문에 일관성을 유지하는 것은 매우 중요하다 &#46; 

- ex) <code>null</code> 값 → <strong>NullPointException</strong>

<details>
<summary>일관성을 유지하는 방법</summary>

- <code>캡슐화</code>
    - 객체의 속성을 <code>private</code>로 선언하고 <code>getter</code> 와 <code>setter</code> 메서드를 통해 제어한다&#46;
        - 외부에서의 접근을 제한하여 객체의 상태를 직접 수정될 수 없게 한다&#46;

        - 잘못된 값이 설정되는 것을 방지하고 객체가 항상 유효한 상태를 유지하도록 한다&#46; 

- <code>유효성 검사</code>
    - 메서드나 생성자에서 입력값을 확인하고, 필요한 경우 예외를 던진다&#46; 

- <code>불변성</code>
    - 객체를 불변으로 유지하면 자연스럽게 일관성을 높일 수 있다 &#46;
        - 객체가 변하지 않기 때문에 처음 할당 시에만 유효한 값을 넣으면 된다&#46;

</details>

</details>

## 객체의 상태 초기화 방법

---

<details>
<summary><strong><code>방법 1</code></strong><strong>)</strong> <strong>&#91;</strong> <strong>🤬 </strong><strong>Bad Case &#93;</strong><code>Setter</code>를 사용한 유효성 검사 및 필드값 초기화 &#45;  캡슐화 <strong>O</strong><strong>,</strong> 일관성 <strong>O</strong><strong>, </strong>불변성 ❌</summary>

<a id="1c3eda9b0fe181539673e8d76a0c28e7"></a>

```java
public class ConsistentObject {
    private int value;

    public void setValue(int newValue) {
        if (newValue >= 0) { // 상태 유효성 검증
            this.value = newValue;
        } else {
            throw new IllegalArgumentException("Value must be non-negative");
        }
    }

    public int getValue() {
        return value;
    }
}
```

- Setter를 통해 상태에 값이 할당되기 전, 값이 유효한지 검사를 한다&#46;

- 그러나 Setter를 사용하기 때문에, 언제든지 상태의 값이 외부에서 변경될 수 있다&#46; 
    <a id="1c3eda9b0fe181ad915fd981723bffba"></a>

    → 변하지 않는 상태(불변성) 유지할 수 없다&#46;<br>

</details>

<details>
<summary><strong><code>방법 2</code></strong><strong> )</strong><strong> &#91; 😁 Best Case &#93; </strong>생성자를 통한 유효성 검사 &#45;  캡슐화 <strong>O</strong><strong>,</strong> 일관성 <strong>O</strong><strong>, </strong>불변성 <strong>O</strong></summary>

<a id="1c3eda9b0fe181c0beeee33f34c84878"></a>

```java
public final class Person {
    private final int age;

    public Person(int age) {
        if (age < 0) {
            throw new IllegalArgumentException("Age must be non-negative");
        }
        this.age = age;
    }

    public int getAge() {
        return age;
    }
}

// 사용 예시
Person person = new Person(25); // 유효성 검사 통과
```

- <u>생성자 주입</u> 및 상수(<code>final</code>) 선언을 통해 <code>불변성</code>을 지킨다&#46; 

- 생성자 또한 메서드이기 때문에, <strong>내부</strong>에서<strong> </strong><strong><code>if문</code></strong><strong> </strong>및 <strong><code>예외처리</code></strong>를 할 수 있다&#46; 
    - 이로 인해 상태 값의 <code>일관성</code>을 유지할 수 있다&#46; 

</details>

<details>
<summary><code>방법 3</code> ) 빌더 패턴  &#45; 캡슐화 <strong>O</strong><strong>,</strong> 일관성 <strong>O</strong><strong>, </strong>불변성 <strong>O</strong><strong>, </strong><strong>인자 순서 무시</strong><strong> </strong></summary>

---

- <strong><u>복잡한 객체나 여러 필드가 있는 객체의 경우</u></strong> <strong><code>빌더 패턴</code></strong>을 사용하여 <strong><u>객체 생성 시 유효성 검사</u></strong><strong>를 할 수 있다&#46;</strong>
    - 생성자의 경우, <u>정의한 매개변수 순서를 지키지 않</u>으면 필드에 다른 필드의  상태의 값이 할당될 수 있다&#46; 
        - 타입이 동일한 경우, 컴파일 오류를 발생시키지 않는다&#46; 
            <a id="1c3eda9b0fe18184a54bcf30fbe4ea54"></a>

            → 앱이 클수록 발견하기 어렵다&#46; 따라서 굉장히 해결하기 어려운 오류를 발생시킨다&#46; 

    - 이를 빌터 패턴을 통해 해결한다&#46; 

</details>

## 빌더 패턴 

---

> ✏️ 
> 
> <a id="1c3eda9b0fe181cda306cb0714bfcb47"></a>
> 
> <code>빌터 패턴</code>을 사용한 <u>객체 생성 및 상태값 초기화 방법</u>은 객체 지향의 <code>캡슐화</code>, <code>불변성</code>, <code>일관성</code>을 해치지 않고 상태에 값을 할당할 수 있으며 <strong><u>생성자 사용</u></strong><strong> 시의 </strong><strong><u>인자의 순서를 보</u></strong><u>장</u>해야되는 문제를 해결할 수 있다&#46; 

<a id="1c3eda9b0fe18140a9f3d6c26437398c"></a>

빌더 패턴은 상태 값을 초기화하고자 하는 <strong><u>엔티티 내부에 빌더라는 객체를 만</u></strong>들고<strong><u> 해당 객체를 통해 외부에서 값을 받</u></strong>으며 처리하는 방법을 말한다&#46;&#93;

<details>
<summary>구현 방법</summary>

<a id="1c3eda9b0fe181ef92b8d4450b06df9b"></a>

```java
public class MyClass {
		// final 키워드로 선언하여 불변성을 지킨다.
    private final String field1;
    private final int field2;

    // 5. 엔티티 생성자, private로 선언하여 외부에서 호출되는 것을 막는다. 
    // 넘겨받는 builder의 필드값을 할당한다. 
    private MyClass(Builder builder) {
        this.field1 = builder.field1;
        this.field2 = builder.field2;
    }

    // 2. 인스턴스 생성 없이 외부에서 호출할 수 있도록 static method로 생성한다.
		public static Builder builder() {
        return new Builder();
    }

    // 1. 빌더 객체, static 메서드에서 호출될 수 있도록 static 클래스로 생성
    public static class Builder {
		    // 엔티티와 동일한 필드를 갖도록 한다.
        private String field1;
        private int field2;

        // 3. 각 필드 값을 초기화할 수 있는 setter를 생성한다.
		       // 메서드를 통해 값을 초기화 하기 때문에 순서 상관없이 초기화 가능하다. 
        // this를 리턴하여 체이닝을 사용할 수 있도록 한다.
        public Builder field1(String field1) {
            this.field1 = field1;
            return this;
        }

        public Builder field2(int field2) {
            this.field2 = field2;
            return this;
        }

       // 4. 해당 생성자를 통해 엔티티를 내부에서 생성하고 빌더 객체에 초기화한 상태값들을 넘겨준다.
        public MyClass build() {
            return new MyClass(this);
        }
    }
  }
```

1. 엔티티 내부에 Builder 객체를 생성한다&#46; 
    - Builder 객체는 엔티티와 동일한 필드를 갖도록 설정한다&#46;

1. 엔티티 내부에 <code>&#46;builder()</code> 라는 static 메서드를 만들어 외부에서 <code>&#46;builder()</code>를 통해 Builder 객체를 생성하도록 한다&#46;
    - Builder 클래스도 static으로 만들어야 static 영역에 있는 &#46;builder에서 접근할 수 있다&#46;

1. Builder 객체 내부에 각 필드의 값을 초기화할 수 있는 메서드를 만든다&#46; 
    - <code>this</code>를 반환하여 체이닝이 가능토록 한다&#46; 

1. <code>&#46;build()</code> 메서드를 통해 내부에서 해당하는 엔티티 인스턴스를 생성하고 builder 인스턴스를 넘긴다 
    - 해당 인스턴스를 반환값으로 설정한

1. 엔티티의 private 레벨의 생성자를 만들고 반환받은 builder 인스턴스에서 동일한 필드값들을 가져와 할당한다&#46; 

<a id="1c3eda9b0fe181978648db1f654c91be"></a>

 

</details>

<a id="1c3eda9b0fe1815f8563cdb39060ff0d"></a>

매번 엔티티를 빌더 패턴으로 직접 구현하는 것은 매우 번거로운 일이다&#46; 

<a id="1c3eda9b0fe181d6ae4ee648fc48433d"></a>

이를 롬복을 활용하면 간단하게 사용할 수 있다&#46;

<details>
<summary>롬복 &#45; <code>&#64;Builder</code></summary>

<a id="1c3eda9b0fe181d9ab20e30c4207c094"></a>

롬복의 <code>&#64;Builder</code>  사용 시, 빌더 패턴으로 객체의 값을 초기화할 수 있다&#46; 

- Order 엔티티 내부에 Builder 객체를 자동 생성 해준다&#46;
    - 내부에서 Builder를 생성해주는 <code>&#46;builder()</code> static 메서드를 제공

    - 각 필드의 값을 초기화 할 수 있는 초기화 메서드 제공
        - <code>this</code>를 반환 처리하여 <u>체이닝 사용 가능</u>

    - <code>&#46;build()</code> 메서드 사용 시, 할당된 빌더 객체의 필드(상태) 값들을 엔티티의 필드(상태) 할당한다&#46; 

    - 이를 통해 인자의 순서 상관없이 상태 값 초기화가 가능하다&#46;

package kr.sparta.bulk.order.model;

import lombok.Builder;
import lombok.Getter;

@Getter
@Builder
public class OrderChangeDeliveryStatusRequest implements ProcessorMember {
    private Long id;
    private DeliveryStatus status;

    public Order toOrder(Order order) {
        return Order.builder()
                .id(order.getId())
                .product(order.getProduct())
                .quantity(order.getQuantity())
                .customerName(order.getCustomerName())
                .customerAddress(order.getCustomerAddress())
                .status(status)
                .build();
    }
}

### 정리

---

<a id="1c3eda9b0fe1810da540ca7aed0ad2f9"></a>

생성자를 통한 객체의 상태(필드) 값 초기화도 캡슐화, 불변성, 일관성을 유지하는 적절한 방법이다&#46;

<a id="1c3eda9b0fe181d09763d299f613ac79"></a>

그러나 인자가 많아지면 정의한 생성자의 매개변수의 순서에 맞게 인자를 할당하지 않으면 오류를 발생시킨다&#46; 

<a id="1c3eda9b0fe181ba8fccc465609aa7ef"></a>

만약 동일한 타입을 갖는 필드들이라면 컴파일 오류에서도 잡을 수 없다&#46; 

<a id="1c3eda9b0fe181d98884d4962d03e851"></a>

결국 런타임 시에 발견되는 오류인데, 이럴 경우 매우 크리티컬한 상황이다&#46; <br>(테스트 코드 작성 시 테스트에서 잡을 수 있다&#46; 따라서 테스트 코드를 작성하는 것이 중요하다&#46;)

<a id="1c3eda9b0fe181f4ac2bf813e88010fb"></a>

또한 앱의 규모가 클 경우, 해당 오류를 처리하는데도 비용이 든다&#46;  <br>만약 <code>&#64;AllArgsConstructor</code> 같은 자동 생성의 경우 생성자가 직관적으로 보이지 않기 때문에, 발견하기도 어렵다&#46; 

<a id="1c3eda9b0fe18130ae38e7701b7e7ab1"></a>

이러한 경우를 빌더 패턴을 사용하여 간단하게 해결할 수 있으니, 매개변수가 많은 경우라면 적절하게 사용하는 것이 개발 생산성 향상에 있어 매우 중요할 수 있겠다&#46;

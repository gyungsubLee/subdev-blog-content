### 서면 피드백

<a id="1c3eda9b0fe1809894c8df78e61906f5"></a>

### API 명세 

- [x] 1&#46; request header 값에 쿠키나 세션 정보 등을 같이 적어주시면 더 좋을 것 같습니다&#46;

- [x] 2&#46; 리스트를 반환하는 API 의 경우, ResponseBody 내부 데이터가 &#39;&#91;&#93;&#39; 대괄호로 한번 감싸져있어야합니다 &#33; 

- [x] 3&#46; 회원탈퇴 API 같은 경우 &#39;DELETE /users/{userId}&#39; 와 같이 도메인을 활용하면 좋을 것 같습니다&#46;

- [x] 4&#46; 리뷰 생성 API 에서 Path Variable로 orderId를 받고 있는데, orderId는 무조건 앞에 &#39;/orders&#39; 가 나와야합니다 &#33; 

<a id="1c3eda9b0fe180d3aad5deba6bf9d756"></a>

### ERD 작성 

- [x] 1&#46; 어차피 주문 개수는 1개로 고정이기 때문에, Orders 테이블에 quantity 컬럼은 필요없을 것 같습니다 

- [x] 2&#46; User 테이블에 is&#95;active 로 회원 탈퇴 여부를 확인하는 것 같은데, 만약 datetime 타입의 &#39;deleted&#95;at&#39; 과 같이 컬럼을 가져간다면<br>    언제 탈퇴를 한건지 그 시점까지도 추적할 수 있습니다 &#33;

- [x] 3&#46; User 테이블에 저장될 비밀번호는 bcrypt로 암호화 됩니다&#46; bcrypt로 암호화 한 텍스트의 최대 길이는 72바이트이므로, VARCHAR의 길이를 좀 더 작게 조절해도 될 것 같습니다&#46;
    -   참고&#58; https&#58;//security&#46;stackexchange&#46;com/questions/39849/does&#45;bcrypt&#45;have&#45;a&#45;maximum&#45;password&#45;length/

### 최종 피드백

<a id="1c3eda9b0fe180d0b9cae1910d047f45"></a>

```java
< 피드백 >
ERD
1. 잘 구현해주셨지만, 필수 과제가 아닌  도전과제 내용도 고려해서 설계하시는 것도 개인적으로 한번 꼭 해보시길 추천드립니다.

시연영상
1. API 단위로 잘 구성하셨으나 실제 데이터 변경이 있었는지도 중요하니 포함해주시면 더 좋겠습니다. 
2. 실패나 중요한 예외에 대해서도 설명해주시면 더 좋겠습니다.

버전관리
1. .gitKeep 파일이 거의 모든 디렉토리안에 존재하던데, 이러한 파일들은 커밋되지 않도록 팀원분들이 직접 제외시킨 뒤 commit & merge 하셔야합니다 !

ReadMe
1. 아주 잘 작성하섰어요!! 

구현
1. User 회원가입 시, Email 이 올바른 형식인지 확인하는 코드가 없네요 ㅜㅜ 간단하게 SignUpRequestDto 에서 @Email 을 email 필드 위에 선언하면 체크할 수 있습니다 !
2. domain별로 exception을 위치시키는것보단 common > exception 디렉토리에 모여있는게 더 좋을 것 같습니다 !
3. 리뷰 생성 시 엄밀히 따지면 주문 한개당 리뷰 하나를 달 수 있는 것이니 대소관계를 따져보면 "/reviews/orders/{orderId}" 보단 "/orders/{orderId}/reviews" 로 URL을 가져가는 게 더 
    좋을 것 같습니다 !
4. 전체적으로 JPA 에서 기본적으로 제공하는 메서드 (findBy~~, existsBy ~~, countBy~~) 만을 이용해서 구현할 수 있는 쿼리를 @Query 를 이용하여 작성한 부분이 종종 보입니다 !
    간단한 쿼리같은 경우 메서드 네이밍만으로 쿼리가 동작하도록 (개발자 리소스를 줄이기 위해) 고안된 기술인만큼 사용할 수 있으면 사용하시면 좋습니다 !
5. constants 도 domain 별이 아닌 아예 common > constants 에 모두 모여있는 게 좋을 것 같습니다.
6. StoreService 에서 UserService 의존성 주입을 받고 있는데, 이러면 나중에 순환 참조 문제가 발생할 우려가 있습니다 !
    Service에선 웬만하면 Repository 의존성 주입을 받는 걸 추천드립니다 !
7. AuthController 에서 AuthService 에 대한 변수명이 loginService 네요 ! 이건 클래스명에 맞게 통일해주셔야 혼동하지 않을 것 같습니다.
8. 현재 세션에 로그인 중인 사용자의 정보를 모두 담고 있는데, 이러면 민감한 정보까지 같이 세션에 담길 수 있기 때문에 정말 필요한 정보만 따로 담는 게 좋습니다 !
9. 이미 로그인 중인 사용자의 모든 정보를 세션에 담고 있는데, 그 세션에 있는 사용자의 정보를 빼서 굳이 또 한번 사용자를 DB에서 조회하는 로직이 종종 보입니다 ㅠㅠ.
10. 메뉴 삭제 시 메뉴의 상태만 삭제 상태로 변경되어야 하는데 실제로 DB에서 삭제해버리고 있네요 ㅜㅜ soft delete 에 대해 한번 찾아보시면 좋을 것 같습니다. 
      (또는 Menu 테이블에 'status' 라는 컬럼을 추가해서 해당 컬럼으로 '삭제','운영' 여부를 나타내셔도 됩니다)
11. User 테이블에서 deletedAt 이 null이면 삭제되지 않은 유저이고, 무언가 값이 있다면 삭제된 유저이기 때문에 굳이 'isDeleted' 라는 컬럼을 추가할 필요는 없습니다 !

그 외엔 모두 잘 하셨습니다 !
```

###  API 명세서가 없거나 제대로 안 적혀 있으면 발생될 수 있는 문제점

- 개발 협의 불가
    <a id="2ff0b04ef50a4fb3a62f0cbd4f9e0c9a"></a>

    회의 때, 공통 확인 문서가 있어야 한다&#46;

    <a id="2c3ff3959dce45acbd044622ab6e6d62"></a>

    공통 확인 문서가 없으면, 매번 같은 이야기로 리소스가 계속  든다&#46; 

    <a id="49adf5fc955d409ba1b3e05b8acaed0d"></a>

    기능 목록을 확인할 수 없으므로 개발 공수(기간)를 예측할 수 없다&#46;

    - 개발 공수 예측 → ‘얼마나 걸릴까요?’ 무조건 물어본다&#46; 

    - 일단 3일 해보고 피드백 해드리겠다&#46; → 우선 이렇게 말하고 진행

    - 매일 저녁(퇴근 전, 오후 5시 쯤 … )마다 진행사항 공유

    - 이력서 채용 공고  → 원할한 커뮤니케이션 → 현 작업 진행 상황 자주 공유 

- 동시 개발 진행 불가
    <a id="0eca39aa3fc243e79e3c8fa82cd500c8"></a>

    API 문서가 없기 때문에 프론트 개발자들은 어떤 스펙으로 응답이 오는지 알 수 없어 개발을 진행할 수 없다&#46; 

    <a id="99b1609db47a49dfbc6cd4c2edae6631"></a>

    특히 개발 일정이 촉박하여 1시간도 아까운 경우 일정의 문제가 생길 수 있다&#46;

    <a id="514fb69de9c54a3c9ebd5906bf9be45a"></a>

    개발을 진행하더라도 백엔드 개발자에게 구두 또는 채팅으로 계속 문의를 해야 한다&#46; → 개발 시간 지연

    -  구도 or 채팅으로 문의 → 개발 시간 지연

- 테스트 어려움
    <a id="15866c60034444bf85e7b934c6d100de"></a>

    일부 회사에서는 QA팀에서 API를 테스트하기도 합니다&#46; 이 때 API 명세서가 없다면 QA들에게 모든 API에 대해 설명해야한다&#46; 

    <a id="62246986ac6441f4939cb87812d6c428"></a>

    → 굉장히 비효율적

<a id="86c3e260254e4d29a2aeb3208cdd72fa"></a>

결론적으로 API 명세서를 작성하는 이유는 아래와 같다 &#46;

1. 원활한 커뮤니케이션

1. 개발 일정 예측

1. 개발 과정의 효율

> ☝🏻 API 명세서는 남이 읽어보지만 <strong><u>나를 위해 쓰는 것</u></strong>

<a id="15967ad9c50b46b2afd8054922cee1ed"></a>

API 명세서를 제대로 작성하지 않으면, 같은 팀프로젝트 개발자 A, B  C … 등 에서 계속 같은 내용을 설명해야 할 수 있다&#46;

( 같은 일을 업무에 대한 진행이 이뤄지지 않음 )

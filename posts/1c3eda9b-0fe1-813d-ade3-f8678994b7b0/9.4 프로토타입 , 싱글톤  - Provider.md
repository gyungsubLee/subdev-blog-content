> 이전 <a href="#/post/1c3eda9b-0fe1-81a8-92d2-fd8aa2528471">페이지</a> 에서 싱글톤 빈과 프로토타입의 빈을  같이 사용 시, 프로토타입의 빈이 싱글톤 빈과 같은 스코프를 갖는 문제점이 있었다&#46;<br>이번 챕터에서는 Provider 통해 해당 문제를 해결하는 방법들을 다룬다&#46;

<a id="1c3eda9b0fe181aeba69e8bec4fa0386"></a>

### 방법1&#58; 스프링 컨테이너에 요청

> 가장 간단한 방법은 싱글톤 빈이 프로토타입을 사용할 때마다, 스프링 컨테이너에 새로 요청하는 것이다&#46; 

<a id="1c3eda9b0fe181d290a2efbc3f079a05"></a>

```java
package hello.core.scope;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Scope;

import static org.assertj.core.api.Assertions.assertThat;

public class PrototypeProviderTest {
    @Test
    void providerTest() {
        AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext(ClientBean.class, PrototypeBean.class);

        ClientBean clientBean1 = ac.getBean(ClientBean.class);
        int count1 = clientBean1.logic();
        assertThat(count1).isEqualTo(1);

        ClientBean clientBean2 = ac.getBean(ClientBean.class);
        int count2 = clientBean2.logic();
        assertThat(count2).isEqualTo(1);
    }

    static class ClientBean {
        @Autowired
        private ApplicationContext ac;

        public int logic() {
            PrototypeBean prototypeBean =ac.getBean(PrototypeBean.class);
            prototypeBean.addCount();
            return prototypeBean.getCount();
        }

    }

    @Scope("prototype")
    static class PrototypeBean {
        private int count;

        public int getCount() {
            return count;
        }

        public void addCount() {
            count++;
        }

        @PostConstruct
        public void init() {
            System.out.println("PrototypeBean.init " + this ); // this 값 조회 시 인스턴스 참조값? 확인 가능
        }

        @PreDestroy
        public void destroy() {
            System.out.println("PrototypeBean.destroy");
        }
    }
}
```

> <code>ac&#46;getBean()</code>을 실행하면 항상 새로운 프로토타입 빈이 생성되는 것을 확인할 수 있다&#46;<br>이렇게 의존관계를 외부에서 주입 받는 것이 아닌 <strong><u>직접 필요한 의존관계를 찾는 것</u></strong><u>을 </u><u><code>Dependency Lookup(DL) 의존관계 조회(탐색)</code></u> 이라 한다&#46;

> 해당 방법은 애플리케이션 컨텍스트 전체를 주입시키는 방법으로, 코드를 스프링 컨테이너에 종속적으로 만들고, 단위 테스트도 어렵게 만든다&#46; <br>→ 🧐  애플리케이션 컨텍스트 = 스프링 컨테이너, 따라서 스프링 컨테이너를 중첩 생성하여 주입? 

> 지금 필요한 기능은 지정한 프로토타입 빈을 컨테이너에서 대신 찾아주는 딱&#33; <strong>DL</strong> 정도의 기능만 제공하는 무언가가 있으면 된다&#46;<br><strong>스프링에는 이미 모든게 준비되어 있다&#46;  (</strong><del><strong>영화 한 장면 대사 같네…)</strong></del>

## 방법2&#58; ObjectProvider

> <code>ObjectProvider</code> 를 통해 지정한 빈을 컨테이너에서 대신 찾을 수 있다&#46;  (DL, Dependency Lookup) <br>(과거에는 <code>ObjectFactory</code>를 사용하였음, 여기에 편의 기능을 추가해서 <code>ObjectProvider</code> 가 만들어짐)

<a id="1c3eda9b0fe1810fb900e936dc657d33"></a>

```java
@Autowired
private ObjectProvider<PrototypeBean> prototypeBeanProvider;

public int logic() {
   PrototypeBean prototypeBean = prototypeBeanProvider.getObject();
   prototypeBean.addCount();
   int count = prototypeBean.getCount();
   return count;
}
```

> 실행해보면 <code>prototypeBeanProvider&#46;getObject()</code> 을 통해서 항상 새로운 프로토타입 빈이 생성되는 것을 확인할 수 있다&#46;

<a id="1c3eda9b0fe181f78f90d3fe913324ad"></a>

 → <code>ObjectProvider</code> 의 <code>getObject()</code>  호출 시, 내부에서는 스프링 컨테이너를 통해 해당 빈을 찾아서 반환함 (<strong>DL)</strong><br>→ 스프링이 제공하는 기능이지만 기능이 단순하여 단위테스트를 만들거나 mock 코드를 만들기는 훨씬 쉬어짐<br><code>ObjectProvider</code> 는 지금 딱 필요한 DL 정도의 기능만 제공한다

<a id="1c3eda9b0fe181928033f46b46209a6e"></a>

<strong>특징</strong>

> ObjectFactory&#58; 기능이 단순, 별도의 라이브러리 필요 없음, 스프링에 의존<br>ObjectProvider&#58; ObjectFactory 상속, 옵션, 스트림 처리등 편의 기능이 많고, 별도의 라이브러리 필요 없음,<br>스프링에 의존

<a id="1c3eda9b0fe181969f51d2640ef7ff79"></a>

## 방법3 &#58; Provider

<a id="1c3eda9b0fe1815db4b1db787a1ec6e1"></a>

<code>jakarta&#46;inject&#46;Provider</code>라는 JSR&#45;330 자바 표준을 사용 <strong>( 스프링 부트 3&#46;0 이상</strong> )

> <strong>스프링부트 3&#46;0 이상<br></strong><code>jakarta&#46;inject&#58;jakarta&#46;inject&#45;api&#58;2&#46;0&#46;1</code> 라이브러리를 gradle 에 추가

<a id="1c3eda9b0fe1818b8aa0f483c8256ddf"></a>

```java
@Autowired
private Provider<PrototypeBean> provider;

public int logic() {
   PrototypeBean prototypeBean = provider.get();
   prototypeBean.addCount();
   int count = prototypeBean.getCount();
   return count;
}
```

<a id="1c3eda9b0fe181c79385ca45da3407ce"></a>

<code>provider&#46;get()</code> 실행 → 매번 새로운 프로토타입 빈 생성

<a id="1c3eda9b0fe1814b9b04ccdb281dbce6"></a>

⇒ <code>provider&#46;get()</code> 호출 시, 스프링 컨테이너를 통해 해당 빈을 찾아 반환 ( <strong>DL</strong> )

<a id="1c3eda9b0fe181e2aa5ef02c708d70e4"></a>

⇒ 자바 표준, 기능 단순하여 단위테스트르 만들거나 mock 코드를 만들기 쉽다&#46;

> 요청 시, 프로토타입 빈 생성됨, 이전 싱글톤에서는 찾지 못함&#46; 방법1은 애플리케이션 컨텍스트 전체를 주입합

<a id="1c3eda9b0fe181f781ceeff8772333b8"></a>

⇒ 스프링 컨테이너에서 생성되는 프로토타입 빈을 찾고 반환하는 동작을 수행 ( 방법1 과 같이 무겁지 않음)

<a id="1c3eda9b0fe181d68968c4a3fd0e0ceb"></a>

  

<a id="1c3eda9b0fe181f5b336ca4f0234997e"></a>

<strong>특징</strong>

> <code>get()</code> 메서드 하나로 기능이 매우 단순<br>별도의 라이브러리 필요<br>자바 표준으로 스프링이 아닌 다른 컨테이너에서도 사용 가능

## •  정리

---

<a id="1c3eda9b0fe18156877ae2e0c2580798"></a>

사용할 때 마다 의존관계 주입이 완료된 새로운 객체가 필요 → 프로토타입 빈 사용

<a id="1c3eda9b0fe181859a8ce24b1d848125"></a>

싱글톤 빈으로 대부분의 문제를 해결할 수 있기 때 문에 프로토타입 빈을 직접적으로 사용하는 일은 매우 드물다&#46;<br><code>ObjectProvider</code> , <code>JSR330 Provider</code> 등은 프로토타입 뿐만 아니라 DL이 필요한 경우는  사용 가능

> ⚠️ <strong>참고</strong>
> 
> > 실무에서 자바 표준인 JSR&#45;330 Provider 과 스프링이 제공하는 ObjectProvider 중 어느 것을 사용해야 하는가?
> 
> <a id="1c3eda9b0fe18101a1f7e2900b00214d"></a>
> 
>  ObjectProvider는 DL을 위한 편의 기능을 많이 제공해주고 스프링 외에 별도의 의존관계 추가가 필요 없기 때문에 편리하다&#46; 
> 
> <a id="1c3eda9b0fe181bc860efc06881cf64d"></a>
> 
> 만약(정말 그럴일은 거의 없겠지만) 코드를 스프링이 아닌 다른 컨테이너에서도 사용할 수 있어야 한다면 JSR&#45;330 Provider를 사용해야한다&#46;
> 
> <a id="1c3eda9b0fe181adbf3ee1404702e0e4"></a>
> 
> 스프링을 사용하다 보면 자바 표준과 스프링이 제공하는 여러 기능들이 겹칠때가 많은데, 대부분 스프링이 더 다양하고 편리한 기능을 제공해주기 때문에, 특별히 다른 컨테이너를 사용할 일이 없다면, 스프링이 제공하는 기능을 사용하면 된다&#46;

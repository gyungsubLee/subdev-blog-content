### 왜 개발자를 선택하셨나요?

<a id="18feda9b0fe1804ea923c3804cddd7fd"></a>

취미로 공부를 시작했다가, 생각보다 적성에 맞아서 진로를 선택하게 되었습니다&#46;

<a id="18feda9b0fe18063bee1d84c4977c971"></a>

 공부를 하고, 해당 내용을 정리 및 이해를 하며, 그에 맞게 구현을 하는 이 과정이 꽤 재밌는 것 같습니다&#46; 

<a id="18feda9b0fe180a8a30ac15e4ce69ad4"></a>

아직까지 베포나 서비스 운영을 해보지는 못하였으나, 실제 내가 만든 서비스가 사용자가 사용하며 그에 따른 가치 창출이 이뤄진다면 굉장히 보람차고 재밌을 것 같다고 생각하고 있습니다&#46; 

<a id="18feda9b0fe18052b52ac3dab5ce9fbc"></a>

### 현재 진행중인 프로젝트의 간단한 서비스 소개와 본인이 담당한 부분을 사용한 기술 내용과 함께 적어주세요&#46;

<a id="18feda9b0fe18093881ac3f3bd34ff26"></a>

프로젝트 이름은 Connect이고 각 개인 마다 본인들의 취미에 해당하는 활동들을 계획하고 비슷한 사람들을 매칭하여 소통하도록 도와주는 앱입니다&#46;

<a id="18feda9b0fe180c3b3a2c60de3b6b238"></a>

담당한 기능은 채팅이며 전체적인 프로젝트 코드에서 약 10%정도 차지하지만 메인 기능 중에 하나로써 중요도는 약 25% 정도를 차지하고 있는 것 같습니다&#46; 

<a id="18feda9b0fe1809a830ac7f708f11826"></a>

### 지난번에 본인 구현 파트를 00이라고 설명해주셨는데, 사용하신 기술 00에 대해 관련해서 설명 해주세요&#46;

<a id="18feda9b0fe18042bd3cf4e3fbcffff6"></a>

제가 구현한 기능은 채팅입니다&#46; 

<a id="18feda9b0fe180a58354dec29c053610"></a>

기술적인 의사결정에 있어서는 &#91; HTTP, WebSocket &#93;,&#91; redis, rabbitMQ &#93;를 고려 했습니다&#46;

<a id="18feda9b0fe18051b7c1cb94ca08eb5f"></a>

프로젝트의 특성상 유저들끼리 실시간 채팅이 필요했습니다&#46; 이를 기존의 HTTP 통신만으로는 지속적인 connection과 통신에 대한 state를 유지하는 어렵다고 판단되어 Websocket을 도입하였습니다&#46; 

<a id="18feda9b0fe180728ab0d2084bbff228"></a>

이로 인해 첫 TCP/IP handshake 이후 세션을 state 및 connection을 유지하면서 실시간으로 통신할 수 있었고, 양방향 통신을 통해 서버에서 요청없이 클라이언트로 채팅을 보내는 실시간 채팅 서비스를 구현할 수 있었습니다&#46;

<a id="18feda9b0fe180cab605edb334bdbf47"></a>

또한 STOMP를 사용하여, 엔드포인트에서 동적으로 roomId을 식별하여 각 room 마다 발행되는 메세지를 격리시켜 브로드캐스트 처리하여 특정 채팅방에 해당되는 유저들에게 메세지를 전송할 수 있었습니다&#46;

<a id="18feda9b0fe180d692ddc7ccb5f1dcdb"></a>

spring에서는 STOMP를 지원하기 위해 SimpleBroker라는 메세지 브로커를 사용하는데, <br>이는 pub/sub 방식을 지원하는 메모리 기반의 메세지 브로커입니다&#46; 

<a id="18feda9b0fe180f093f0ff649a822589"></a>

따라서 트래픽 증가에 따른 scale out 시, 분산 서버 환경에서 동기화 문제가 발생될 수 있습니다&#46; 

<a id="18feda9b0fe180d5ace5fdabc141d524"></a>

또한 메모리를 사용하기 때문에 서버에 많은 부하를 줍니다&#46; 

<a id="18feda9b0fe18001ab60d93ab0148974"></a>

이러한 내용을 고려하여 동기화 문제 및 부하 분산 처리를 위해 외부 미들웨어를 추가하기로 하였습니다&#46; 

<a id="18feda9b0fe18003b16ed622beee2b82"></a>

미들웨어에 대한 구현은 여러 기술이 있지만  그 중 2가지 내용을 고려하여 redis 와 rabbitMq를 선택했습니다&#46; 

- 엄청 큰 트래픽(큰 수억 • 수천만 단위) 상황은 고려하지 않는다&#46; 

- 시중에서 많이 사용 되는 기술을 사용한다&#46;

<a id="18feda9b0fe180599482e6b350fad9af"></a>

redis와 rabbitMQ의 장단점을 비교하자면,

<a id="18feda9b0fe180abbb8acdd5163eaf79"></a>

redis는 인메모리 기반으로 빠른 처리가 가능하다는 장점이 있지만, <br>싱글쓰레드로 동기적인 처리만 가능하고, 메세지에 대한 영속성(persist) 처리가 필요하며, 라우팅 기능만을 제공해 메세지가 중간에 소실되는 경우 retry에 대한 처리가 추가로 필요하는 단점이 있습니다 &#46;

<a id="18feda9b0fe180329c91cd9e4c834591"></a>

rabbiMQ는 redis에 비해 메세지 처리 속도가 낮으나, 메세지의 persist(저장)나 실패에 대한 retry 매커니즘을 제공하고 비동기(병렬) 처리가 가능하다는 장점이 있습니다&#46; 

<a id="18feda9b0fe1800baa1cf83d6663e881"></a>

신뢰성 있는 서비스를 구성하기 위해서는 메세지 전송 실패 시, retry 처리가 필수적으로 필요했습니다&#46;

<a id="18feda9b0fe180698be8e1afa2e4cf74"></a>

 이를 내부적으로 제공하는 rabbitMQ를 사용하면 개발 생산성을 높이고 이후, 유지보수 포인트를 낮추게 되며 또한 비동기적 처리가 가능하므로 속도에 대한 문제도 해결할 수 있다고 판단 하였고,

<a id="18feda9b0fe180bb9c29d3438295e39d"></a>

따라서 외부 미들웨어에 대한 구현 기술로 rabbitMQ를 사용하기로 결정했습니다&#46; 

<a id="18feda9b0fe180aa956dfbcbb30cc757"></a>

이를 통해, 서버에 대한 부하를 분산 처리 및  scale out 시, 발생될 동기화 문제를 해결할 수 있었습니다&#46;

### Java에서 쓰레드(Thread)와 프로세스(Process)의 차이점은 무엇인가요?

<a id="18feda9b0fe1801684b2fc202ce60e9d"></a>

프로세스는 운영체제로 부터 자원을 할당 받은 작업의 단위로, 실행 중인 프로그램의 인스턴스 입니다&#46; 

<a id="18feda9b0fe180659a7fcc9d394b9e09"></a>

스레드는 프로세스 내에서 실행되는 흐름의 단위로 프로세스가 할당받은 자원을 공유하며 동작합니다&#46; 

<a id="18feda9b0fe18007bf6cdc041ee3d919"></a>

하나의 프로세스는 여러의 스레드를 가질 수 있습니다 &#46;

<a id="18feda9b0fe1800b9fb3cf92df53abb2"></a>

### 추가 질문) 프로세스와 스레드의 메모리 구조 및 격리성에 대해 차이점은 무엇인가?

<a id="18feda9b0fe180ee9433fbaa7c8787d3"></a>

프로세스는 독립적인 메모리 공간을 가지며, 스레드는 Stack만 개별적으로 할당되고, 나머지는 공유합니다&#46; 

<a id="18feda9b0fe18044b220fa0b24037abb"></a>

따라서 프로세스는 다른 프로세스와  메모리를 공유하지 않으며, 스레드는 동일 프로세스 내에서는 스레드끼리 메모리를 공유합니다&#46; 

<a id="18feda9b0fe180b48376e7271b2912e0"></a>

### 추가 질문) 프로세스와 스레드의 생성 및 자원 관리에 대해서 차이점은 무엇인가?

<a id="18feda9b0fe180819d60e9f6660ee90a"></a>

프로세스는 생성 시 운영체제가 별도의 메모리 공간을 할당 하므로 시간이 많이 소요됩니다&#46;

### OSI 7 계층 중 전송 계층(Transport Layer)의 역할과 TCP와 UDP의 차이점은 무엇인가요?

<a id="18feda9b0fe180d5828bf4c158d69bc9"></a>

OSI 7 계층에서의 전송 계층은 4번째에 해당되는 계층으로, 송신자와 수신자 간의 신뢰성 있는 데이터를 전송 보장하는 역할을 합니다 &#46;

<a id="18feda9b0fe18057a620deec2728916b"></a>

Port 번호를 통해 식별하며, 데이터 전송의 단위는 segment 입니다&#46; 

<a id="18feda9b0fe1801caa1dfa78417ce27a"></a>

일반적으로 HTTP version1 통신에 사용되는 TCP에만 connection, session, state에 대한 개념이 있으며, 

<a id="18feda9b0fe180eb81d4c790f1dcab49"></a>

UDP는 이러한 개념이 없기 때문에 상대의 수신 여부와 관계없이 데이터를 보냅니다&#46;

<a id="18feda9b0fe1800fad21e9400266499a"></a>

TCP의 경우 출발지 포트, 목적지 포트, 일변번호, 확인 응답 번호, 헤더길이, 예약영역, 윈도우 크기, 긴급 포인터 등… 정형화된 헤더에 많은 정보를 담아 통신하지만

<a id="18feda9b0fe180cea5a2cee8e5775299"></a>

UDP의 경우, 출발지 포트번호, 목적지 포트 번호, 길이, 체크섬 등 경량화면 정보만 담고 있기 때문에, 영상 송출이나, 게임 서버 등에서 사용됩니다&#46;

### 팀 프로젝트에서 기술적 의견 차이를 극복한 경험이 있나요?

<a id="18feda9b0fe180519b90f4d2ec500653"></a>

팀프로젝트에 대한 경험은 내일 배움 캠프가 처음이라, 짧은 경험 상으로는 좋은 팀원들을 만나 기술적인 의견 차이는 없었던 것 같습니다&#46; 

<a id="18feda9b0fe1809d8339eb44a3470fb4"></a>

그러나 기술적인 의견 차이에 대한 극복 경험은 아니지만, 기술적인 의사결정이 왜 중요한지 마지막 팀프로젝트에서 배울 수 있었습니다&#46; 

<a id="18feda9b0fe180f9b4c2f64fd140e600"></a>

이에 대해서 짧게 말씀드리자면,최종 프로젝트에서 팀적으로 프론트엔드에 대한 부분을 추가로 개발하기로 논의가 되었습니다&#46; 

<a id="18feda9b0fe180eb94d6ccbe8320e9cd"></a>

프론트에 대한 기술 스택으로 react, typescript를 사용하기로 하였는데, 개발 공부 초창기에 리액트에 대해 짧게 학습한 경험이 있어 해당 결정에 대해 크게 생각을 하지 않고 결정을 받아 들였으나,

<a id="18feda9b0fe18091a276d89d6697ae4a"></a>

오히려 프론트 기술에 대한 러닝 커브가 백엔드에 대한 부분보다 컸고, <br>예상 외 프론트에 대한 학습에 더 많은 시간을 소모되어 맡은 기능에 대해서 시간에 구현하지 못하는 문제가 발생되었습니다&#46; (이는 팀원을 도움을 받아 해결했습니다&#46;)

<a id="18feda9b0fe1805bb228f2b3eb6f3d2c"></a>

이로인해, 기술에 대한 난이도, 주어진 기간, 개인의 역량에 따라서 기술 스택에 대한 논의가와 결정이 이뤄져야 된다는 것을 크게 배울 수 있었고

<a id="18feda9b0fe18091a5e8fd8c0701bb44"></a>

또한 이후 팀에서 기술적인 스택에 대해 고민할 때, 이러한 부분 고려하여 팀적으로 잘 소통하고 의견을 조율하는 것이 중요하다는 것을 학습할 수 있었습니다&#46;

<a id="18feda9b0fe18081915dc1f857a67cf9"></a>

### 이후 팀 프로젝트를 진행한다면 어떻게 기술 의견 차이를 극복할 것인가?

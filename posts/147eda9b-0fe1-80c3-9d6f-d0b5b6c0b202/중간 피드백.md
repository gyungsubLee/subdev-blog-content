<summary>API 명세</summary>

- 전 기능 공통 전달사항 &#45; 데이터와 명세를 분리하셨네요&#46; 상황마다 다르겠지만, API 명세서 작성 시 표 안에 request/response 데이터를 명시하면 바로 확인할 수 있어서 개발 시 용이할 수 있습니다&#46; 지금도 일부 URL이 다르네요 ㅠㅠ&#46; 일단 아래에 있는 상세 기준으로 작성했습니다&#46; &#45; 전체적으로 예제/샘플 데이터는 잘 작성되어 있는편이지만, 설명이 부족합니다&#46; 

- 어떤 기능을 하는 API인지 description이 추가적으로 있으면 좋을것같습니다&#46; &#45; 401 Unauthorized와 400 Bad Request, 500 등&#46;&#46; 실패 시 어떤 조건에서 해당 상태 코드를 반환하는지 명시해주세요&#46; 지금 작성된 기준으로는 모르겠습니다&#46; 

- 응답(response) 데이터 포맷이 모두 다릅니다&#46; 에러 메시지와 함께 통일해주시면 더 좋을것같습니다&#46; { &#34;status&#34;&#58; &#34;success&#34;, &#34;data&#34;&#58; {&#46;&#46;&#46;}, &#34;message&#34;&#58; &#34;게시글 등록 성공&#34; }, { &#34;errorCode&#34;&#58; &#34;USER&#95;NOT&#95;FOUND&#34;, &#34;message&#34;&#58; &#34;해당 유저를 찾을 수 없습니다&#34; } 등

- 회원가입 &#45; 성공 응답의 상태 코드가 201 Created와 200 OK로 혼용되고 있습니다&#46; RESTful API의 관례에 따라 회원가입 시 201 Created로 통일하시는것이 좋아보입니다&#46; &#45; redirect&#58; /login은 HTTP 헤더에 Location 필드로 명시하거나 클라이언트가 직접 처리하도록 명세에서 분리하는 것이 좋습니다&#46;

- 로그인 &#45; 응답 헤더의 HttpOnly와 Secure 필드는 true/false 대신 실제 설정 값으로 작성하면 더 명확해서 좋습니다&#46;

- 로그아웃 &#58; 문제되는점은 보이지 않습니다&#46;

- 회원탈퇴 &#45; 삭제된 사용자 데이터의 후속 처리(비활성화 상태로 변경)를 명세에 포함하면 더 좋습니다&#46;

- 개인 프로필 API &#45; 프로필 조회 &#58; 요청 PathVariable인 id 대신, 현재 로그인된 사용자에 한해 조회 가능하도록 /users/me 같은 엔드포인트로 변경하는것이 좋아보입니다&#46; id 변경 시 자신 이외의 사용자를 조회할 수 있는지, 정책상 문제가 없는 기능인지 확인이 필요합니다&#46; &#45; 프로필 수정 &#58; 수정자 본인이 본인 데이터를 수정하는것인지 내부 로직에서 검증이 필요합니다&#46;

- 게시글 정보 API &#45; 게시글 작성 &#58; multipart 데이터 사용시 파일 업로드 크기 제한 등을 명세에 추가해주시는것이 좋아보입니다(ERD 수정 선행 필요)&#46; 그리고 성공응답(201 Created)에서 생성된 게시글 ID 외에, 게시글이 작성된 시간과 같은 추가 정보를 반환하시면 더 좋습니다&#46; &#45; 게시글 조회 &#58; 이미지 데이터의 반환 형식에 경로만 반환하실까요? 혹시 어떻게 파일을 가져오실 계획인지 명확해야 할것같습니다&#46; (base64 등) &#45; 게시글 수정 &#58; 요청 데이터에서 빈 필드가 전달되면 무시하도록 하거나 에러를 반환하도록 명세에 포함하시는것이 좋아보입니다&#46; 그리고 게시글 비밀번호 따로 없다보니, 작성자와 로그인 된 세션정보가 일치 해야 수정이 가능하도록 내부 로직을 구현해야할 것 같습니다&#46; &#45; 게시글 삭제 &#58; 작성자와 로그인 된 세션정보가 일치 해야 삭제가 가능하도록 내부 로직을 구현해야할 것 같습니다&#46;

- 친구 관리 API &#45; 친구 추가 &#58; 공통 전달사항만 확인하시면 될것같습니다&#46; &#45; 친구 수락 &#58; 서비스의 성격/기획에 따라 성공 응답 데이터에 업데이트된 친구 리스트 반환을 고려해볼수도 있을것같습니다&#46; 필수기능은 아니니 참고만 해주세요&#46; &#45; 친구 삭제 &#58; 삭제 성공시 응답에 친구 삭제 결과 메시지를 주는것이 좋아보입니다&#46;

<summary>ERD</summary>

- 댓글, 좋아요 등의 도전 기능을 당장 구현하지 않더라도, 추후 구현할 가능성이 있기 때문에 확장성을 고려해서 설계까지는 해두었으면 합니다&#46;
    - FRIEND 테이블에 별칭(nickname), 설명(description)이 추가되면 더 재밌는 앱이 될것같아요&#46; 그리고 친구를 리스트를 정렬하기 위해서 우선순위(priority) 컬럼이 추가되면 좋을것같습니다&#46;

    - IMG 테이블의 생성 일자 컬럼명은 create&#95;date이고, 나머지는 create&#95;at인데, DB에서 공통적으로 사용되는 컬럼은 하나의 컨벤션 규칙으로 묶어서 통일 해주시는것이 좋습니다&#46;

    - 회원탈퇴 기능을 위해 USER 테이블에서 사용하는 컬럼이 사용여부(useryn)뿐 인듯한데, 보통 user&#95;status/status같은 직관적인 명칭으로 관리하고, 탈퇴날짜(leave&#95;at/leave&#95;date) 컬럼을 추가해주시는것이 좋습니다&#46;

    - 이미지 테이블에 파일 크기(file&#95;size) 컬럼도 추가되면 좋을것같아요&#46; 보통 파일 업로드시 사이즈 제한을 두고 개발합니다&#46;

</details>

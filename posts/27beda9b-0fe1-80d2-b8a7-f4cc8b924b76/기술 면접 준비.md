<details>
<summary>N&#43;1 문제</summary>

- 정의 
    - 1 번의 쿼리로 N개의 데이터를 가져왔는데 <strong><u>연관된 데이터를 참조할 때마다 추가로 N 번의 쿼리가 더 발생</u></strong>하는 현상 ( 총 1 &#43; N 번)

- 해결책&#58; <strong>Fetch Join</strong>
    - 처음부터 <code>JOIN</code>을 써서 쿼리 1번에 모든 데이터를 다 가져오는것 

> ✏️ 
> 
> <a id="308eda9b0fe1801fa2ade859d36847ff"></a>
> 
> <strong>실무 권장</strong>
> 
> <a id="308eda9b0fe180b78461f7709d2d15b7"></a>
> 
> 가장 권장되는 전략은 <strong>기본은 닫고(</strong><strong><code>Lazy</code></strong><strong>), 필요할 때만 연다(</strong><strong><code>Fetch Join</code></strong><strong>)</strong>
> 
> - 모든 연관 관계를 <code>FetchType&#46;LAZY</code>로 설정합니다&#46; (불필요한 데이터 로딩 방지)
> 
> - 능 최적화가 필요한 특정 조회 화면(게시판 목록 등)에서만 <strong>JPQL의 </strong><strong><code>Fetch Join</code></strong>이나 <strong><code>EntityGraph</code></strong>를 사용해 딱 필요한 연관 데이터만 한 번에(Eager하게) 가져옴

</details>

<details>
<summary>질문) 운영 중인 웹 서비스에서 갑자기 데이터베이스 쿼리 성능이 저하되는 현상이 발생했습니다&#46; 로그를 확인해 보니 특정 API 엔드포인트에서 N&#43;1 문제가 발생하고 있다는 것을 발견했습니다&#46; 이 문제를 어떻게 해결하시겠습니까?</summary>

- 우선 N&#43;1 문제가 발생하는 상황을 정확하게 파악합니다&#46; 
    - 보통 ORM을 사용할 때 연관된 엔티티를 조회하는 과정에서 발생하는 문제로, 

    - 예를 들어 게시글을 가져오면서 각 게시글의 작성자 정보를 개별적으로 조회하는 경우 이런 문제가 발생합니다&#46;

- 해결 방안으로 크게 두가지를 고려해 볼 수 있습니다&#46;
    - 첫 번째는 <strong><u>이거 로딩(Eager Loading)</u></strong>을 사용하는 방법입니다&#46;<br><strong> JPA를 예로 들면 </strong><strong><u>페치 조인(Fetch Join)</u></strong><strong>을 사용</strong>해서 연관 엔티티를 한 번의 쿼리로 함께 조회하는 방법입니다&#46; 

    - 두번째 <strong><u>배치 사이즈(Batch Size)를 설정</u></strong>하는 방법입니다&#46; <br>완전한 이거 로딩이 부담스러운 경우 배치 사이즈를 설정해서 정해진 숫자로 끊어서 조회하는 방법이 있습니다&#46;

</details>

<details>
<summary>질문) 언급하신 해결책들을 적용했을 때 이러한 성능 개선이 실제로 효과가 있었는지 어떻게 측정하고 모니터링 하시겠습니까?</summary>

- 개선 전후 정확하게 비교하기 위해서는 몇 가지 지표들을 측정해야 합니다&#46; 
    - 첫번째로 응답 시간을 모니터링 합니다&#46; 
        <a id="308eda9b0fe180f6aaf6f5f2f97ef47c"></a>

        특히 해당 API의 P95, P99 응답 시간을 측정하는데, 이는 대부분의 사용자가 경험하는 실제 성능을 반영하기 때문입니다&#46; 

        <a id="308eda9b0fe180d3a85ac988eca26cc2"></a>

        이를 위해 프로메테우스와 그라파나 같은 모니터링 도구를 활용할 수 있습니다&#46; 

    - 두번째로 데이터베이스 관련 메트릭을 확인합니다&#46; 
        <a id="308eda9b0fe18045ba36e476f59b1303"></a>

        실행되는 쿼리의 수가 얼마나 줄었는지, 각 쿼리의 실행 시간은 어떻게 변했는지 등을 측정할 수 있습니다&#46; 

        <a id="308eda9b0fe180b9ad6dd017188b091e"></a>

        이를 위해서는 슬로우 쿼리 로그 같은 기능을 활성화하고 데이터베이스 모니터링 도구를 사용할 수 있습니다&#46; 

    - 세번째는 서버 리소스 사용량을 체크합니다&#46; 
        <a id="308eda9b0fe180b58713c805a371b24a"></a>

        CPU, 메모리 사용량, DB 커넥션 수 등의 변화를 관찰하여 개선이 전반적인 시스템 성능에 미치는 영향을 파악합니다&#46; 

    - 그리고 이러한 모니터링은 단발성이 아니라 지속적으로 이루어져야 합니다&#46; <br>예를 들어 트래픽이 많은 시간대나 특정 이벤트 기간에도 개선된 성능이 잘 유지되는지 확인해야 합니다&#46;

<summary>질문) 네트워크 계층에 대해서</summary>

- 네트워크 계층은 OSI 7 계층 중 3개의 계층이 해당하며 데이터를 출발지에서 목적지까지 라우팅하고 전달하는 계층이다 &#46;이 계층에서 사용하는 주요 프로토콜로는 인터넷 프로토콜인 IP, ICMP 그리고 ARP 등이 있다&#46;

</details>

<details>
<summary>질문) 네트워크 계층 프로토콜에 대해서 조금 더 자세히 설명</summary>

- IP는 네트워크 계층의 핵심 프로토콜로 데이터를 작은 패킷으로 나누고 이를 전달하는 역할을 한다&#46; 

- ICMP는 Internet Control Message Protocol의 약자로 네트워크에서 문제가 발생했을 때 사용하는 프로토콜이다&#46; <br>예를 들어 핑(ping) 명령어가 ICMP를 사용하여 목적지 호스트가 응답하는지 확인하거나 네트워크 연결에서 문제가 있는지 진단한다&#46; 

- ARP는 Address Resolution Protocol의 약자로 네트워크 계층에서 사용되는 IP 주소를 물리적인 MAC 주소 변환하는 프로토콜이다&#46; <br>예를 들어 패킷이 목적지 IP 주소를 알고 있지만 해당 IP에 대응하는 MAC 주소를 모를 때 ARP를 사용하여 IP를 MAC 주소로 변환하고 패킷을 전송하낟&#46; 

</details>

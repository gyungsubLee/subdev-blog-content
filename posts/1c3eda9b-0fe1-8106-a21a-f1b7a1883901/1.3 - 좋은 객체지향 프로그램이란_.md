### 객체 지향 프로그래밍

<a id="1c3eda9b0fe181888317f3537332f90b"></a>

객체 지향 프로그래밍은 컴퓨터 프로그램을 명령어의 목록으로 보는 시각 벗어나 <u>여러 개의 독립된 단위, 즉 </u><u>“</u><strong><u>객체</u></strong><u>”들의 </u><strong><u>모임</u></strong><u>으로</u> 파악하고자 하는 것이다&#46; <br><u>각각의 </u><strong><u>객체</u></strong><u>는 </u><u>메세지를 주고 받</u><u>고, </u><u>데이터를 처리</u>할 수 있다&#46;(협력)

<a id="1c3eda9b0fe18128ace9def2145cadcd"></a>

객체 지향 프로그래밍은 프로그램을 <strong>유연</strong>하고 <strong>변경</strong>이 용이하게 만들기 때문에 대규모 소프트웨어 개발에 많이 사용된다&#46; 

<a id="1c3eda9b0fe181a49301d927bbe72c01"></a>

### 유연하고, 변경 용이?

<a id="1c3eda9b0fe18134a77ee8454678ba8c"></a>

레고 블럭 조립하 듯, 컴퓨터 부품을 갈아 끼우듯이

<a id="1c3eda9b0fe1817d8206cc85dc41accc"></a>

<u>컴포넌트를 쉽고 유연하게 변경</u><u>하면서 개발</u>할 수 있는 방법  → <code>다향성</code>(객체지향의 핵심)

<a id="1c3eda9b0fe181ab9bebd91fa6df2863"></a>

### 다형성(Polymorphism) 실세계 비유

> <strong>실세계 &#58;  객체 지향  → 1&#58; 1 매칭 X</strong><br>(그래도 실세계 비유가 이해하기 가장 수월함&#46;)

<a id="1c3eda9b0fe181c2b2d8ef130daa400a"></a>

세상을 <strong><code>역활(인터페이스)</code></strong><strong> </strong>과 <strong><code>구현(인스턴스)</code></strong><strong> </strong>으로 구분

<a id="1c3eda9b0fe18167b2a7d7ccc579b3b9"></a>

### 예시1 ) 운전자 &#45; 자동차

![](876aafb748ae8b90.webp)

> 자동차 역활(인터페이스) → 3개의 자동차 구현( K3, 아반떼, 테슬라 모델3)

<a id="1c3eda9b0fe1817b8666cd5d113131a1"></a>

운전자는 K3를 타다가 아반떼로 자동차를 바꿔도 운전을 할 수 있다&#46; <br>왜냐하면 자동차의 종류(구현)만 변화하였을 뿐, 자동차 내부 동작(역할)은 동일하기 때문이다&#46; 

<a id="1c3eda9b0fe181769ddffd62774fff6e"></a>

따라서 자동차가 바뀌어도 운전자가 운전을 하는데 있어서 필요한, 운전면허증, 운전 방법에 영향을 주지 않는다&#46; 즉, 자동차의 구현체가 변해도 자동차의 역할(인터페이스)은 변하지 않으며,  운전자(클라이언트)에게 아무런 영향을 주지 않는다&#46; (운전자는 자동차 역활에 대해서만 의존한다&#46;)

<a id="1c3eda9b0fe181aea38bd40c3c7504b9"></a>

이것을 ‘유연하고 변경이 용이하다’고 표현하며, 이러한 방식이 객체지향의 다형성의 특징이다&#46; 

<a id="1c3eda9b0fe18151aa2fd1ba526c2412"></a>

<code>클라이언트</code>는 <strong>내부 애플리케이션의 구현이 변경</strong>되어도, <code>인터페이스</code>에만 의존하기 때문에,영향을 받지 않는다&#46; 

<a id="1c3eda9b0fe1810d8917d7dcf9f3e4e7"></a>

즉, <strong> 클라이언트에 영향을 주지 않고 내부 구현 로직을 변경 할 수 있다</strong>는 엄청난 확장성과 유연성을 가진다&#46; 

<details>
<summary>예시2) 공연무대</summary>

![](1a702da57e0c04c1.webp)

<a id="1c3eda9b0fe1814e9c5cfabadd5645a3"></a>

위 공연처럼 극 중 <code>캐릭터 역할</code> 과 <code>그 역할을 연기하는 배우</code> 가 나눠서 각 역할(interface)가 독립적이고, 배우가 바뀌어도 캐릭터 역할 자체에는 아무런 영향을 주지 않는다&#46; 

</details>

<a id="1c3eda9b0fe18103b938cb8e182ba835"></a>

## <code>역활</code> , <code>구현</code> 분리 (객체 지향(<code>다형성)</code>의 핵심 의미)

> <strong>• 역할  =  인터페이스</strong><br><strong>• 구현  =  인터페이스를 구현한 클래스, 구현 객체(인스턴스)</strong>

<a id="1c3eda9b0fe1813c8669e40c8a1a21c6"></a>

<code>역활</code>과 <code>구현</code>으로 구분하면 세상이 <strong>단순</strong>해지고, <strong>유연</strong>해지며 <strong>변경도 편리</strong>해진다&#46; 

<a id="1c3eda9b0fe181088940e7fc665b31a7"></a>

## 장점

> <strong>• 클라이언트</strong>는 대상의 <strong>역활(인터페이스)만 의존</strong>한다&#46; <br><strong>• 클라이언트</strong>는 구현 대상의 <strong>내부 구조를 몰</strong>라도 된다&#46; <br><strong>• 클라이언트</strong>는 <u>구현 대상의 </u><strong><u>내부 구조가 변경</u></strong><u>되어도 영향을 받지 않</u>는다&#46;<br><strong>• 클라이언트</strong>는 구현 <strong>대상 자체를 변경</strong>해도 영향을 받지 않는다&#46; 

<a id="1c3eda9b0fe181fc9dcbd87f45cc32b8"></a>

### 객체 설계

> • <code>역할</code> 과 <code>구현</code> 을 명확히 분리<br>• <u><code>역할(인터페이스)</code></u><u> 정의</u> → <u>그 역할을 수행하는 </u><u><code>구현 객체</code></u><u>를 생성</u>

<a id="1c3eda9b0fe1814490b2d9b4a0d52a2d"></a>

<strong>인터페이스</strong>가 아닌 <strong>일반 상속 관계</strong>도 다형성 구현이 가능하다&#46;

<a id="1c3eda9b0fe181c08b94e2d4e8357549"></a>

그러나, <strong><u>인터페이스</u></strong><u>는</u><strong><u> 다중</u></strong><u>으로 </u><strong><u>상속</u></strong><u> 구현이 가능</u>하지만,<br><strong>일반 상속 관계</strong>는 <strong>단일 상속</strong>만 되며, 그 외 여러가지의 문제점들이 존재한다&#46; 

> <strong>인터페이스를 상속 ⇒ 다형성 구현(권장)</strong> <br>( <code>역활(인터페이스)</code>  &#62;&#62;&#62;  구현)

<a id="1c3eda9b0fe1813b9317f6cf17d35f25"></a>

### 객체의 협력 관계(클라이언트 ↔ 서버)

<a id="1c3eda9b0fe181f98d31cc8b3c95af67"></a>

혼자 있는 객체는 없다&#46; 

> 클라이언트(요청) ↔ 서버(응답)

<a id="1c3eda9b0fe181d7a708c1bf88508b06"></a>

수많은 객체 클라이언트 와 객체 서버는 서로 협력 관계를 가진다&#46;

![](7b7d56bf19a2862d.webp)

## 정리

<a id="1c3eda9b0fe18158bf76ccedf517dff4"></a>

실세계의 &#91; 역할 &#45; 구현 &#93; 이라는 편리한 컨셉을 다형성을 통해 객체 세상으로 가져올 수 있다&#46;

<a id="1c3eda9b0fe181b3862ff7a95511220a"></a>

⇒ 인터페이스를 안정적으로 잘 설계해야함&#46;

<a id="1c3eda9b0fe181549c43c0b0fbf17fbe"></a>

### 스프링 &#45; 객체 지향(<code>다형성</code>)

- 스프링은 다형성을 극대화해서 이용할 수 있게 도와준다&#46; 

- 스프링에서 이야기하는 제어의 역전(IOC), 의존관계 주입(DI)은  다형성을 활용해서 역활 과 구현을 편리하게 다룰 수 있도록 지원한다&#46;

- 스프링을 사용하면 마치 레고 블럭을 조립하듯, 구현을 편리하게 변경할 수 있다&#46;

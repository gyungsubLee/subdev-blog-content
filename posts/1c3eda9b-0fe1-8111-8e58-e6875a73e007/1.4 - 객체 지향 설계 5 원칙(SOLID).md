# SOLID

<a id="1c3eda9b0fe181fbbdb2f000907833e1"></a>

클린 코드로 유명한 로버트 마틴이 좋은 객체 지향 설계의 5가지 원칙을 정리

> • SRP&#58; 단일 책임 원칙(single responsibility principle)<br>• OCP&#58; 개방&#45;폐쇠 원칙(Open/Closed principle)<br>• LSP&#58; 리스코프 치환 원칙(Liskov substitution principle)<br>• ISP&#58; 인터페이스 분리 원칙(Interface segregation principle)<br>• DIP&#58; 의존관계 역전 원칙(Dependency inversion principle)

<a id="1c3eda9b0fe1819a9f35ff25d4a9ec09"></a>

## SRP (단일 책임 원칙)<br>single responsibility principle

> 한 클래스는 하나의 책임만 가져야 한다 &#46;

<a id="1c3eda9b0fe18149948cf3b9909d3a87"></a>

하나의 책임이라는 개념이 실질적으론 참 모호한 개념이다&#46; <br>책임은 클 수도 있으며, 작을 수도 있고, 문맥과 상황에 따라 다르다&#46; 

> <strong>중요한 기준</strong>은 <strong>변경</strong>이며, 변경이 있을 때, <strong>파급 효과 가 적으면 단일 책임 원칙을 잘 따른 것</strong>이다&#46; 

<a id="1c3eda9b0fe18188b540e2ed981ea6a3"></a>

하나의 클래스가 하나의 지점만 고치면 단일책임원칙을 잘 따르는 것이다&#46; 

<a id="1c3eda9b0fe181b3b8c8c9d27325dea4"></a>

ex) UI변경, 객체의 생성과 사용 분리

> <strong>계층(layer)</strong>를 나누며 개발을 하는 것이 다 SRP(단일책임원칙)을 잘 지키기 위해서다&#46;

> 책임의 범위를 적절히 잘 조절하는 것이 중요하다&#46; 

<a id="1c3eda9b0fe1818dadd9f924b5b5a449"></a>

범위가 너무 작으면 DB가 너무 작게 쪼개지고 너무 크게 설계하면 책임이 너무 많이져 여러개의 책임이 담길 수 있다&#46; 

<a id="1c3eda9b0fe1814eb00dd1328ac343ff"></a>

## OCP (개방&#45;폐쇄 원칙)<br>Open/closed principle

> 소프트웨어 요소는 <strong>확장에는 열려</strong> 있으나, <strong>변경에는 닫혀</strong> 있어야 한다&#46;

<a id="1c3eda9b0fe181a3b72cee480bec04d2"></a>

<strong><code>다형성</code></strong>(<strong>&#91; 역활 &#45; 구현 &#93; 분리 ) </strong>을 활용하면 가능하다&#46; 

<a id="1c3eda9b0fe181d08000d7506722e49e"></a>

→ interface(고정) → 구현 객체 (확장) 

<a id="1c3eda9b0fe18172b736da9d6b45c5bd"></a>

결국에는 interface를 잘 설계하는 것이 중요하다&#46; 

<a id="1c3eda9b0fe18188a238d7d6e885faa9"></a>

## LSP 리스코프 치환 원칙<br>Liskov substitution principle

<a id="1c3eda9b0fe1814f81a3f66fa2c7aed6"></a>

## ISP&#58; 인터페이스 분리 원칙<br>Interface segregation principle

<a id="1c3eda9b0fe18146b449d8bae97e6040"></a>

## DIP&#58; 의존관계 역전 원칙<br>Dependency inversion principle

> interface(추상화, 역할)에 의존 해야한다&#46; <br>(interface(역할)  &#62;&#62;&#62;&#62;&#62; 구현 )

<a id="1c3eda9b0fe18174bc47f0cacec63a4b"></a>

## 정리

<a id="1c3eda9b0fe181b7a995c591f0644c1a"></a>

객체 지향의 핵심은 다형성이다&#46;

<a id="1c3eda9b0fe181ab837ffc37d5258567"></a>

그러나 다형성 만으로는 쉽게 부품을 갈아 끼우듯이 개발할 수 없다&#46;

<a id="1c3eda9b0fe18164b3cec18506181b98"></a>

다형성만으로는 구현 객체를 변경할 때, 클라이언트 코드도 함께 변경된다&#46; 

<a id="1c3eda9b0fe181978607c7f0ba522cb1"></a>

### 다형성 만으로는 OCP, DIP 를 지킬수 없다&#46;
